# Spec: multi-account support

Status: **all 6 stages done and live-verified — this feature is complete.** Interviewed to find the real goal before scoping, matching this project's other multi-stage passes (e.g. "custom-categories," "Bill reminders via Web Push"). A Plan agent cross-checked this spec against the actual codebase before implementation began and found two corrections, folded in below: `wipeLocalAccountData()` re-seeds a default account rather than wiping to empty, and the new ledger module is named `accounts.js` (plural) to avoid colliding with the existing, unrelated `account.js` (signed-in Google identity tracking).

## Goal

Right now every transaction belongs to one implicit ledger per user — there's no way to know which physical account (cash on hand, a bank account, a credit card) a given transaction actually came out of, or what any one of those accounts' balances should be.

Interviewed to find the actual driver, since "add accounts" could mean several different things: the answer was **reconciling each account's running balance against a real bank/card statement.** That's a materially different goal from "just tag transactions with a label" — it means an account's balance can't simply be "sum of transactions ever entered in the app," because a real account already had a balance before the user started using whereisit. This is why an opening balance field (below) is in scope even though it wasn't in the original request.

## Decisions (confirmed via interview)

1. **Reconciliation is the goal**, not separating spending purposes or a pure "where does my money physically sit" overview. This is what justifies the opening-balance field and the "selected account" default below.
2. **Accounts get an opening balance**, set at creation. Running balance = opening balance + all transactions logged against that account. Without this, the balance would never match a real statement for any account that existed before the user started logging in the app.
3. **Home's hero card defaults to one selected account's balance**, not a combined total — switching the selected account changes the hero balance together with the rest of Home's account-scoped content (see decision 7 below for exactly what that includes). This matches "check one account against its statement at a glance."
4. **The Home switcher also offers an "All accounts" combined option** alongside each individual account — useful for an overall glance, not just single-account reconciliation.
5. **No transfer transaction type in this pass.** Moving money between the user's own accounts (cash deposit into the bank, paying a credit card from the bank) is out of scope — it would need a transaction that touches two accounts at once and is excluded from income/expense totals so it doesn't double-count. Ship single-account transactions and correct reconciliation first; transfers can be a later spec.
6. **Budgets, bills, and goals stay global** — not scoped to any one account, tracked against all transactions regardless of account, exactly as today. Accounts affect transactions and balances only in this pass.
7. **Transactions screen gains an account filter** (added to its existing Filters sheet, alongside type/category/date/amount) — needed to actually review one account's full transaction list against a statement. Insights (breakdown charts/budgets tab) stays untouched; an Insights account breakdown would be a follow-up spec if wanted.
8. **Archiving an account doesn't hide it.** An archived account disappears from the Add screen's account picker (can't be a target for new transactions) and from "active" defaults, but stays visible in Home's switcher and Transactions' filter — e.g. to check a closed account's final reconciled balance. This is why the schema uses an `archived` flag rather than hard delete, per the original request.

## Why this needs a schema change, not just new UI

Every transaction, budget, and bill in this app currently has no notion of "which account." Supabase's `transactions` table (confirmed via direct introspection of the live project, not assumed) has `id text primary key`, `user_id uuid references auth.users(id)`, `type`, `tx_date`, `category`, `category_id`, `amount numeric`, `note`, `deleted`, `updated_at` — no account column at all. Giving each transaction a real `account_id` and each account its own row (with an opening balance to reconcile against) is a genuine schema migration across a new table plus one existing table, which is why this is staged rather than one change — the same shape as `custom-categories.md`'s `category_id` migration.

## Decisions made without a direct question (flagged for review before building)

- **`accounts` gets a single-column `id text primary key`, not the composite `(id, user_id)` key `categories` uses.** Directly answering the open question in the original request: `categories` needed the composite key because its 16 *built-in* categories are seeded with the exact same fixed id (e.g. `default-expense-food`) across every user's account on purpose (confirmed via `supabase/migrations/20260829060000_categories.sql`'s own comment) — a single-column PK would reject the second user's row as a duplicate the moment two accounts both seed the same built-in id. Accounts have no equivalent: even the one default "Cash" account created per user (see backfill below) gets a normal, per-user-unique client-generated `uid()`, the same as every transaction/budget/bill/goal/push_subscription row already does. So `accounts` follows that existing single-column pattern, and `sync.js`'s `pushRows()` — which already special-cases `table === "categories"` to pass `{ onConflict: "id,user_id" }` — needs **no new special case for `accounts`**; it falls through the same unqualified `.upsert(chunk)` path transactions/budgets/bills/goals already use.
- **The default "Cash" account created per user during backfill gets `opening_balance: 0`, not a guessed nonzero value.** This is what makes the migration a true no-op for every existing user's *displayed* balance: today's Home balance is exactly `sum(all transactions)` with no opening-balance concept at all (confirmed by reading `home.js`'s current hero-card calculation), so a `0` opening balance on the account that inherits every pre-existing transaction reproduces that exact same number. Any other default would silently change a real number every existing user is used to seeing, the moment this ships.
- **Account icon set**: a small new curated list in `categories.js`-style (`ACCOUNT_ICON_CHOICES`), reusing `wallet`, `credit-card`, and `piggy-bank` from the existing sprite, plus one genuinely new icon — `landmark` (a bank building glyph) — since nothing in the current 41-icon sprite reads as "bank account" the way `credit-card` clearly reads as "credit card." Added the same way `bell`/`log-out` were added in earlier passes: fetched from the same pinned `lucide-static@1.35.0` every other sprite symbol comes from, inserted alphabetically, re-verified with a real XML parser.
- **New account default in the Add screen's picker**: defaults to the same account last used in a saved transaction (mirrors how the category picker already remembers the user's last manual pick via `state.categoryManual`-style behavior, not literally that field), falling back to the first non-archived account if there's no prior transaction yet (e.g. right after the default "Cash" account is created). Never defaults to an archived account.
- **`markBillPaid` (`home.js`) needs an account too**, since it creates a transaction under the hood the same as the Add screen does. Defaults to Home's currently-selected account if one specific account is selected (not "All accounts"), else falls back to the same "first non-archived account" rule as the Add screen. Flagged because the original request didn't mention this call site, but it's a real transaction-creation path exactly like Add and needs to carry a real `account_id` for the same reason stage 4/5 of `custom-categories.md` had to fix this exact call site for `categoryId`.
- **Reconciling an apparent tension between two interview answers**: decision 3 above says switching Home's account selector changes "the hero balance, recent-activity list, and budget preview" (that was the option's own wording when it was picked); decision 6 says budgets stay global and track all transactions regardless of account. Resolving this in budgets' favor (decision 6 is the more specific, later-confirmed answer): Home's **budget preview panel and upcoming-bills list do not change when the account switcher changes** — only the hero balance, the income/expense stat cards, the "spent today" card, and the recent-activity list scope to the selected account (or combine across all accounts when "All accounts" is selected). This keeps Home internally consistent with decision 6 rather than contradicting it.
- **Archiving is blocked if it would leave zero active (non-archived) accounts.** Every new transaction needs a real account to save against, so at least one active account must always exist — mirrors the spirit of existing guards elsewhere in this app (e.g. categories' in-use delete guard), though the mechanism here is different (archive-blocking, not delete-blocking, since archiving is non-destructive).
- **No "in use" delete guard is needed at all**, unlike categories' delete flow — because accounts are never hard-deleted in this feature (archived flag only, per the original request), an account with existing transactions can always be safely archived without orphaning anything; its transactions and balance stay exactly as they were, just no longer a target for *new* transactions.

## Staged build plan

### Stage 1 — `accounts` table + sync plumbing (additive, no behavior change yet) — done
New Supabase table: `id text primary key, user_id uuid not null references auth.users(id) on delete cascade, name text not null, icon text not null, opening_balance numeric not null default 0, archived boolean not null default false, updated_at timestamptz not null default now(), deleted boolean not null default false`. RLS matching the existing pattern exactly (one `ALL` policy, `auth.uid() = user_id`, `to authenticated`). New migration file following the existing naming convention (`supabase/migrations/<timestamp>_accounts.sql`).

`state.accounts` array + `setAccounts` setter (`state.js`), seeded locally with one default "Cash" account (`opening_balance: 0`) the same way `budgets`/`bills` already ship with sample defaults — so a fresh, never-signed-in install already has a valid account to save transactions against. `storage.js` persists `accounts` inside the existing `SETTINGS_KEY` blob alongside budgets/bills/goals/categories, via the same `restoreArray` pattern. `sync.js` gains `rowToAccount`/`accountToRow` mappers and `pullAccounts`, using plain `mergeRowsById` (no quirk to preserve, no `onConflict` needed — see the decision above). `accounts` joins the five-table wiring the other tables already have: `markAllPending`, `syncNow`'s pull/push/`dropPendingForRemovedIds` sequence, and both `pending.js`'s and `watermark.js`'s hardcoded `TABLES` arrays (each currently a literal `["transactions", "budgets", "bills", "goals", "categories"]` plus a matching object-literal — both need a manually-added `"accounts"` entry, not just the array, since the `pending`/`watermark` objects in those two files are separate literals rather than derived from `TABLES`).

**Correction found during implementation planning, not the original interview**: `wipeLocalAccountData()` re-seeds `accounts` back to a single fresh default account (mirroring `categories`' `DEFAULT_CATEGORIES` re-seed) rather than wiping to empty like transactions/budgets/bills/goals. The original draft of this spec put accounts in the "wipe to empty" group on the reasoning that an account is personal data, not app vocabulary — but unlike budgets/bills/goals, having *zero* accounts breaks a real invariant: the Add screen cannot save a new transaction without a valid account to assign it to. That's the same problem categories solve by re-seeding instead of emptying, just via a different code path (a `DEFAULT_ACCOUNT` constant in the new `accounts.js`, not `DEFAULT_CATEGORIES`). Confirmed directly with the user before implementation started, not decided unilaterally.

**Module naming**: the new leaf module is `src/accounts.js` (plural), not `account.js` — that name is already taken by an existing, unrelated module (`src/account.js`, tracking the *signed-in Google identity* for cross-device account-switch isolation — `accountDisplayName`, `shouldWipeLocalData`, already imported by `settings.js`). The new module's equivalent lookup helper is named `accountNameById(accountsList, id, fallback)` to avoid a same-name export collision on top of the same-name file collision.

**Verify (done)**: `npm run build` and `npm test` both pass (90/90, unaffected — no `derived.js` changes yet). Live-verified in a real browser: `localStorage.clear()` + reload confirmed a genuinely fresh install seeds `accounts: [{ id: "acc0", name: "เงินสด", icon: "wallet", openingBalance: 0, archived: false }]` in the `SETTINGS_KEY` blob correctly; zero network requests matching "accounts" and zero console errors on that fresh, signed-out load (confirmed via DevTools-equivalent network/console capture, not just visually). Home rendered unchanged (no visible behavior change, as intended for this stage). The live-project `get_advisors` security check came back with no new findings introduced by the new table/policy. The "confirm the same account id on two real signed-in devices" half of this check is deliberately deferred to Stage 2's verification instead of being done twice — Stage 2 is the first stage with real behavior at stake (the backfill actually moves data), so the one throwaway-account round-trip test happens there and covers both.

### Stage 2 — `account_id` on transactions + backfill + `computeBalance` — done
Add nullable `account_id text` to `transactions` (no FK constraint, matching `category_id`'s precedent exactly — `user_id` is nullable on `transactions` for the same local-only-user reason `category_id`'s migration documents, and application-level lookups plus RLS already handle the edge case without needing Postgres to enforce it).

One-time client-side backfill (`sync.js`, same shape as `backfillCategoryIds`): if the signed-in/local user has no accounts yet beyond whatever's already locally seeded, ensure the default "Cash" account exists (creating it with `opening_balance: 0` if genuinely missing — e.g. an existing user who already has cloud data from before this feature shipped), then stamp every transaction lacking an `account_id` with that account's id, push just the changed rows through the existing chunked `pushRows`, gated behind a one-time local flag exactly like `backfillCategoryIds`'s `BACKFILL_KEY`.

New pure function in `derived.js`, **unit-tested like the module's other pure functions**: `computeBalance(accountId)` — `accountId: null` means all accounts combined (sum of every active-or-archived account's opening balance, plus every transaction regardless of account); a specific id means that one account's opening balance plus only its own transactions' income-minus-expense. Deleted/archived accounts are still included when combined (their balance is real money that existed), just not selectable for new transactions (a UI-layer restriction, not a math one).

**Verify (done)**: `npm run build` and `npm test` pass (96/96 — 6 new `computeBalance`/`defaultAccountId` cases). Real Supabase round-trip tested against the live project via a throwaway auth user (created and fully deleted afterward, same technique as the "Categories upsert onConflict investigation" section): pushed the default account row and a transaction carrying `account_id` through the actual REST API with the exact request shape `pushRows`/`accountToRow`/`txToRow` produce, pulled both back filtered by `user_id` (simulating a second device's pull), confirmed RLS scoped correctly and every field (including the Thai account name) round-tripped byte-for-byte — all test rows and the throwaway user deleted after. ## Follow-up: chip-style account picker on Add/Edit (post-ship)

Requested directly after the feature shipped: the Add/Edit form's account field was still a bare `<select>` while the category field right above it already has an icon-led chip row. `screens/add.js` gained `renderAccountChips()`, mirroring `renderCategoryChips()`'s visual pattern but simpler — a user's account list is always small (unlike categories, which can run into dozens), so every available account gets its own chip directly with no ranked top-N/"more" overflow needed. The underlying `<select id="txAccount">` stays in the DOM as the real form control `wireAddForm`'s submit handler reads from, just always visually collapsed (`.account-select-collapsed`) rather than conditionally collapsed like `.category-select-collapsed`, since there's no overflow case here. New CSS: `.account-chip-row` (mirrors `.category-chip-row`'s layout) and `.account-chip .icon` (the existing `.account-chip`/`.account-chip.active` from Home's switcher, stage 5, are reused as-is — same concept, "represents one selectable account as a chip," just a different container).

Shared by both `renderAdd()` (desktop) and `renderAddSheet()` (mobile bottom sheet) automatically, since both already call the same `addFormFieldsHtml()`/`wireAddForm()` pair — no separate mobile-specific change needed.

Live-verified in a real browser (both light and dark mode, desktop): chips render with the correct icon (wallet for Cash, landmark for Bank) and label; the current account (from `defaultAccountId()` or the transaction being edited) shows correctly active; clicking a chip updates the hidden `<select>`'s value and re-renders the active state; a real transaction saved through a clicked chip carried the correct `accountId`; opening an existing transaction's edit form correctly pre-selected its chip. Zero console errors. `npm run build && npm test` (99/99) and `npm run test:e2e` (9/9) all pass.

## Explicitly out of scope

- Transfers between the user's own accounts (a dedicated transaction type touching two accounts at once) — see decision 5.
- Per-account budgets, bills, or goals — see decision 6.
- Insights screen (breakdown charts, budgets tab) gaining any account awareness — see decision 7.
- Multi-currency accounts — every account is assumed to be in the same currency the app already displays (THB formatting via `fmtMoney`), matching how the app has never supported multiple currencies for anything else.
- Real bank/card sync or statement import (Plaid-style) — explicitly out of scope per the original request; opening balance + manual entry only.
- Reordering accounts beyond creation order.
- Hard-deleting an account — archive only, per the original request.
