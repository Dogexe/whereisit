# Spec: transfers between accounts

Status: **all 4 stages done and live-verified — this feature is complete.** A direct follow-up to `docs/specs/multi-account-support.md`, which explicitly deferred this ("no transfer transaction type in this pass... ship single-account transactions and correct reconciliation first; transfers can be a later spec"). Interviewed to find the real goal before scoping, matching every other multi-stage pass in this project.

## Goal

Moving money between two of the user's own accounts (a cash withdrawal into the bank, paying a credit card from a bank account) currently has no clean way to record: skip it and both accounts' balances drift from reality, or fake it as an unrelated expense + income pair and pollute spending totals with money that never left the household. The confirmed driver is **pure balance correctness** — keeping both accounts' running balances accurate — not building transfer-history reporting or analytics on top. That framing keeps this spec's scope narrow: get the balances and the transaction list right, don't build a dedicated "transfer history" view or teach Insights anything new about transfers.

## Decisions (confirmed via interview)

1. **Balance correctness is the goal**, not transfer analytics/reporting. This is why nothing here touches Insights, and why a transfer's own "history" is just its row in the existing Transactions list, not a new screen.
2. **A transfer is one record**, not two linked transactions — `type: "transfer"`, a `fromAccountId` (reusing the existing `account_id` column) and a new `toAccountId` column, one `amount`. Viewing the source account shows it as an outflow, viewing the destination shows it as an inflow, viewing "All accounts" hides it entirely (its net effect across the combined view is zero — nothing left the household). One record to edit or delete, always self-consistent, unlike a linked pair that could drift apart if one side's edit fails to reach the other.
3. **Recording a transfer lives on the existing Add form**, as a third type tab (Expense / Income / **Transfer**), not a separate screen. Picking Transfer swaps the account picker for a From/To pair and hides the category field entirely (a transfer has no spending category).
4. **In the Transactions list (not account-scoped by default), a transfer always renders as a neutral, direction-labeled row** ("Cash → Bank," its own icon, no +/− sign or income/expense coloring) regardless of any active account filter — not a context-sensitive sign flip. Only Home (which always resolves to exactly one context — a specific account or "All accounts") shows a transfer signed relative to the account being viewed.

## Why this needs a schema change, and two real correctness bugs it would introduce if not handled carefully

`transactions.type` has a Postgres CHECK constraint, `transactions_type_check`, limiting it to `ARRAY['income', 'expense']` (confirmed by direct introspection of the live constraint, not assumed) — a transfer needs that constraint widened to include `'transfer'`.

More importantly, two existing functions in `derived.js` were written when every transaction was assumed to be income or expense, and both would silently produce wrong numbers the moment a `type: "transfer"` row exists, if left untouched:

- **`computeBalance(accountId)`**'s combined (`accountId == null`) branch reduces every transaction with `t.type === "income" ? +amount : -amount` — a ternary that treats *anything not literally "income"* as a subtraction. A transfer would get silently subtracted from the combined balance twice-over-wrong (it's not income, so `-amount`, when its correct combined effect is exactly zero). Its specific-account branch filters by `t.accountId === accountId` — since a transfer's account fields are `fromAccountId`/`toAccountId`, not `accountId`, it would be *invisible* to a specific account's balance instead, which is just as wrong the other way. Both branches need explicit transfer-aware logic, not a small tweak.
- **`filteredTxList()`'s account-filter clause** (`state.txFilterAccount.has(t.accountId)`, stage 6 of the parent spec) has the identical blind spot — a transfer would never match any account filter at all, since it has no `.accountId`, and would silently vanish from a filtered Transactions list even when its from/to account is exactly what's being filtered for.

Both are existing-code correctness risks this spec surfaces, not new design choices — they're called out explicitly here so the staged build plan below fixes them deliberately rather than as an afterthought once someone notices a wrong balance.

## Decisions made without a direct question (flagged for review before building)

- **Schema stays minimal**: reuse the existing `account_id` column as the transfer's *from* account (no new "from" column needed — for an expense/income row it already means "the account this belongs to," and for a transfer it means the same thing, just paired with a new *to*), and add one new nullable `to_account_id text` column (no FK, same precedent as `account_id`/`category_id`). `category`/`category_id` stay null for a transfer row — it isn't spending, so it doesn't belong to a category, and every existing budget/breakdown function already filters to `type === "expense"` explicitly, so a transfer is naturally excluded from all of them with zero code change there.
- **The hero sparkline (`computeSparklinePoints`) excludes transfers entirely**, rather than trying to make the trend line transfer-aware. It's a decorative trend indicator, not a source of truth (the hero balance number is), so the simpler, lower-risk fix is applied there: filter transfers out before building the day-by-day running net, in both the combined and per-account cases.
- **Validation**: `fromAccountId !== toAccountId` (can't transfer an account into itself), amount `> 0`, both accounts must exist — archived accounts are excluded from being picked as a *new* transfer's From/To, except one already referenced by the transfer being edited (identical rule to the regular Add-screen account picker, applied to both pickers here).
- **`checkBudgetAlert` is never called for a transfer** — the Add screen's submit handler branches on `formType === "transfer"` and skips the budget-alert toast entirely (a transfer was never spending, so there's nothing to alert against).
- **Transactions' existing type filter (`state.txFilterType`, today All/Income/Expense) gains a fourth "Transfer" option** — a one-line radiogroup addition, and `filteredTxList()`'s existing `rows.filter(t => t.type === state.txFilterType)` already works for any type value including `"transfer"` with no further change, so this is close to free once the type exists at all.
- **New sprite icon**: `arrow-right-left` (lucide's canonical bidirectional-arrows glyph), fetched from the same pinned `lucide-static@1.35.0` every other icon comes from, for the Transfer tab and the transfer row's icon.

## Staged build plan

### Stage 1 — schema + sync + derived.js correctness fixes (no UI yet) — done
Migration: `alter table public.transactions drop constraint transactions_type_check; alter table public.transactions add constraint transactions_type_check check (type = any (array['income', 'expense', 'transfer']));` and `alter table public.transactions add column if not exists to_account_id text;` (nullable, no FK, same precedent as `account_id`).

`sync.js`: `rowToTx`/`txToRow` gain `toAccountId`/`to_account_id` (and `txToRow`'s `category` gained a `|| ""` fallback — see the real `NOT NULL` finding below). `derived.js`: `computeBalance(accountId)` fixed per the two bugs above — combined branch filters to `type === "income" || type === "expense"` before reducing, then separately nets every `type === "transfer"` row's effect on the combined total (always zero, but computed explicitly rather than assumed, so the logic is legible); specific-account branch adds a second reduce over transfers, treating `.accountId` as the source (a transfer never gets its own separate "from" field — `.accountId` already means that, per decision 2) and `.toAccountId` as the destination. `computeSparklinePoints` filters out `type === "transfer"` rows in both branches. `filteredTxList()`'s account-filter clause gains `|| (t.type === "transfer" && state.txFilterAccount.has(t.toAccountId))` — the *source* side already matches through the existing `.has(t.accountId)` check with no change needed, since a transfer's source account lives in that same field.

**Verify (done)**: `npm run build` and `npm test` both pass (103/103 — 5 new tests covering the combined-balance-nets-to-zero case, per-account balance moving correctly in both directions, the sparkline excluding transfers, and the account filter matching via either side). Live-verified in a real browser: seeded a Cash (₿0 opening) + Bank (₿5,000 opening) pair with a ₿20,000 income and a ₿300 transfer Cash→Bank, and confirmed by hand-checked arithmetic that "All accounts" showed exactly ₿25,000.00 (the transfer correctly netting to zero rather than being wrongly subtracted), Cash showed exactly ₿19,700.00, and Bank showed exactly ₿5,300.00 (19,700 + 5,300 = 25,000, confirming both sides are internally consistent, not just individually plausible). Also confirmed live that a transfer doesn't yet appear in the destination account's recent-activity list on Home (expected — that's `scopedTx`'s `.accountId`-only filter, Stage 3's job, not a Stage 1 regression) even though its effect on that account's *balance* is already correct.

**A real schema gap found only by testing the actual round trip, not assumed**: `transactions.category` turned out to be a `NOT NULL` column at the database level (a real upsert with `category: null` was rejected with a `23502` constraint violation) — not documented anywhere before this, since every prior transaction type always had a real category string. Fixed in `txToRow` (`sync.js`) with a `t.category || ""` fallback, the same treatment `note` already gets on the line right below it, rather than a second migration to loosen a column that's a legacy display fallback anyway (`category_id` is the real source of truth per `custom-categories.md`). Re-verified after the fix: pushed and pulled back a real `type: "transfer"` row against the live project via a throwaway test account (created and fully deleted afterward, same technique as prior passes) — `type`, `to_account_id`, and the empty `category` string all round-tripped correctly.

## Explicitly out of scope

- Transfer fees / a source amount that differs from the destination amount (e.g. a wire fee) — one `amount`, moved in full.
- Multi-currency conversion on a transfer.
- A dedicated transfer-history view or any Insights awareness of transfers — the goal is balance correctness, not transfer reporting (see the Goal section).
- A "reverse this transfer" or quick-swap-direction shortcut on the Add form.
- Editing a transfer's from/to accounts after the fact in any way other than the same Add/Edit form every other transaction already uses.
