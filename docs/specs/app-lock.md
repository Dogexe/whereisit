# Spec: local app-lock (PIN)

Status: **not started.** Interviewed to find the real goal, then read the current codebase (`main.js`'s boot sequence, `storage.js`'s `SETTINGS_KEY` blob, the sheet-overlay/focus-trap pattern in `utils.js`, `screens/settings.js`'s section-nav structure) before staging a build plan, following this repo's usual staged-spec convention (`custom-categories.md`, `category-nesting.md`).

## Goal

The phone stays signed into Google OAuth persistently — that's fine for identity, but it means anyone who picks up an *already-unlocked* phone can open the installed PWA and see the user's full transaction history at a glance, with zero friction. The fix isn't more auth (Supabase RLS/session handling is explicitly out of scope and stays exactly as-is) — it's a lightweight, purely client-side speed bump: a PIN gate on the app itself, checked against a value stored only in this device's own `localStorage`, never sent anywhere. This is a convenience lock, not a security boundary — the spec and its UX copy should say so explicitly rather than imply otherwise, since overpromising here (e.g. calling it "secure" or offering fake recovery) would be actively misleading to a user who might rely on it for something it doesn't do.

## Decisions (confirmed via interview)

1. **Lock threshold: immediate, not idle-timed.** Any time the app is backgrounded/hidden at all — even briefly — it re-locks on return. No idle timestamp, no configurable grace period. Simplest to implement and reason about, and removes an entire class of "was that 45 seconds or 90?" edge cases a grace-period design would introduce.
2. **Also blur/cover content the instant the app is backgrounded**, not just gate re-entry. The same `visibilitychange`-to-`hidden` handler that arms the lock also applies a CSS cover synchronously, so the OS app-switcher thumbnail doesn't show a plain snapshot of transaction data. Decision 1 (immediate threshold) implies caring about exactly this gap, so leaving it open would undercut the point of choosing "immediate."
3. **PIN format: 4-digit numeric.** Matches the phone lock-screen convention every user already knows, and keeps the entry UI a simple numeric keypad rather than a text input — appropriate friction for a convenience lock, not real security.
4. **Settings placement: new "Security" section**, not folded into Display. Gives the feature room (this spec's own explicitly-deferred WebAuthn follow-up) and keeps Display's purely-cosmetic toggles (language/dark-mode/theme) separate from anything security-adjacent.
5. **Enable flow: inline, same toggle row.** Flipping "Require PIN" on immediately reveals a PIN entry + confirm-entry field right there in the Security section (matching this app's existing inline-form pattern, e.g. Categories' add form) — the toggle only actually turns on once a valid, confirmed PIN is saved. No separate dialog/sheet.

## Decisions made without a direct question (flagged for review before building)

- **No persisted "currently locked" flag — the lock state is derived, not stored.** A cold page load always shows the lock screen if a PIN is enabled (nothing to derive — every fresh load is trivially "was not visible a moment ago"). During a live session, an in-memory (not `localStorage`) boolean is set on `visibilitychange` → `hidden` and checked on `visibilitychange` → `visible`; it resets naturally on every real reload since it was never persisted. This is *simpler* than it first sounds, not a corner cut: it also correctly handles the case where a backgrounded PWA gets fully suspended/terminated by the OS (common on iOS Safari after enough time backgrounded) and "resuming" it is actually a fresh process boot — the cold-load gate covers that case automatically, with no separate detection needed.
- **PIN, its salt, and the enabled flag live inside the existing `SETTINGS_KEY` `localStorage` blob** (`storage.js`'s `saveSettings()`/`loadFromStorage()`), not a new storage key or module. That blob already holds `lang`/`dark`/`themeStyle` — settings that are local-only today, never pushed to any Supabase table (only `budgets`/`bills`/`goals`/`categories`/`accounts`, the other fields in that same blob, get synced, via their own dedicated tables). The PIN fields join `lang`/`dark`/`themeStyle`'s existing "local-only" category rather than inventing a second local-only storage mechanism alongside it.
- **Hashing: salted SHA-256 via the browser's native `crypto.subtle`, not a KDF like PBKDF2/bcrypt, and no new dependency.** Given the explicit "not real security" framing, spending effort on brute-force-resistant hashing would be solving the wrong problem — a 4-digit PIN is 10,000 possibilities either way, and anyone with local `localStorage` access already has full access to the actual transaction data sitting right next to it. The hash's only job is "don't sit in `localStorage` as a readable plaintext PIN for a casual glance," which plain salted SHA-256 already does. A fresh random salt (`crypto.getRandomValues`) is generated once per PIN and stored alongside the hash (both as hex strings) — this rules out a precomputed rainbow-table lookup against the fixed 10,000-value space, which costs nothing extra to add.
- **No attempt lockout / rate limiting on wrong-PIN entry.** Matches the "lightweight convenience lock" framing — the threat model here is an opportunistic glance, not a determined attacker who'd happily sit and brute-force 10,000 combinations even with a lockout in place eventually. A wrong PIN just clears the entry and shows a brief shake/error, no escalating delay.
- **Turning the toggle off does not require re-entering the PIN.** Reaching Settings at all already means the lock was passed for this session (or was never armed as `locked` yet this session) — asking for the PIN a second time to disable it wouldn't add real protection, just friction, and this app doesn't re-authenticate for other Settings actions either (e.g. sign-out).
- **Neither "turn off the toggle" nor "Forgot PIN?" uses a browser `confirm()` dialog** — checked directly against the codebase (`grep -rn "confirm(" src/`) and confirmed this app never uses one anywhere, for any destructive action, including existing category/budget/bill/goal deletes. The actual established pattern (`deleteCategory` et al.) is: act immediately, then offer undo via the same `showToast(message, undoCallback)` shape already used everywhere else (`toast.js`) — a blocking native dialog would be the odd one out here, not the norm. Both flows below follow that existing pattern instead of inventing a confirm-first step.
- **Turning the toggle off**: clears the PIN immediately and shows a toast ("PIN removed") with an Undo action that restores the previous `pinEnabled`/`pinHash`/`pinSalt` — exactly the same shape as `deleteCategory`'s undo restoring a removed category object, just for these three fields instead.
- **"Forgot PIN?" lives on the lock screen itself, not in Settings** — it has to, since Settings is unreachable while locked. Tapping it clears `pinEnabled`/`pinHash`/`pinSalt` and unlocks immediately (same act-then-undo shape as above — tapping Undo on the resulting toast restores the old PIN and re-locks, which is exactly the right behavior if the user actually does remember it a moment later and taps by mistake). This is explicitly **not** account/password recovery — no email, no security questions, nothing server-side — and the link's own label/copy should read plainly as "remove my PIN," not implying any real recovery is happening.
- **The setup PIN entry (Settings' inline form) is a new "live input" case** `hasLiveInputRisk()` (`sync.js`) must guard, the same way every other in-progress form in this app already does — a background sync's `renderSettings()` call mid-setup shouldn't wipe a half-typed PIN.
- **The lock overlay lives in its own empty top-level container** (`#appLockContainer` in `index.html`), matching `#addSheetContainer`/`#manageSheetContainer`'s existing precedent, not inside `#screen`. This means `renderScreen()` calls (including background sync's) never need special-casing around the lock — they keep fully replacing `#screen`'s content exactly as today, just invisible underneath the overlay while locked, so nothing about the underlying screen (an in-progress Add form, a scroll position) is lost across a lock/unlock cycle.
- **No cross-tab lock-state sync.** If two tabs of the app are open, each manages its own in-memory `locked` boolean independently from its own `visibilitychange` events. The PIN itself (hash/salt/enabled) is naturally shared, since all tabs read the same `localStorage`, but one tab locking doesn't force another tab (already visible, already unlocked) to also lock. Multi-tab usage of this app isn't an established pattern elsewhere in the codebase, so this isn't worth the complexity of a `storage`-event listener for v1.

## Overlay pattern precedent (researched, not invented fresh)

This app already has a full-screen-overlay pattern via `.filter-sheet-backdrop`/`.filter-sheet` (`styles.css`) plus three shared `utils.js` helpers: `createFocusTrap()` (Tab-cycling, piggybacked scroll-lock), `sheetGrabberHtml()`/`wireSheetDrag()` (drag handle + swipe-to-dismiss), and `syncSheetToViewport()` (keyboard-safe sizing via `visualViewport`). The lock screen reuses `createFocusTrap()` (so Tab can't leak focus into the covered app behind it) and its piggybacked scroll-lock, and should get `aria-modal="true"`/`role="dialog"` like every other sheet — but it deliberately **skips** `wireSheetDrag()` (a lock screen must not be swipe-dismissible) and the Escape-to-close pattern every other sheet in this app has (`document.addEventListener("keydown", (e) => { if (e.key === "Escape" && state.xSheetOpen) close...() })` — grep confirms one such listener per sheet, keyed to that sheet's own state flag). Skipping both is a deliberate divergence from the base pattern, not an oversight: everything else about a lock screen (full-screen, focus-trapped, scroll-locked, `aria-modal`) matches; being escapable by a swipe or the Escape key would defeat the entire feature.

## Staged build plan

### Stage 1 — core module: state, storage, hashing (no UI yet)
New `src/applock.js`: `state.pinEnabled`/`state.pinHash`/`state.pinSalt` (persisted, joining `lang`/`dark`/`themeStyle` in `storage.js`'s `SETTINGS_KEY` blob per the decision above — both `loadFromStorage()` and `saveSettings()` gain these three fields) and `state.pinSetupActive` (transient, UI-only, for `hasLiveInputRisk()`). Pure-ish async helpers (testable with Node's built-in `crypto.subtle`/`crypto.getRandomValues`, both available globally in a modern Node runtime — no jsdom or browser needed, matching how this codebase's other pure modules get unit tests while screens/DOM code doesn't): `genSalt()`, `hashPin(pin, salt)` (SHA-256 hex), `setPin(pin)` (generates a salt, hashes, sets `pinEnabled`/`pinHash`/`pinSalt`, saves), `verifyPin(pin)` (re-hashes with the stored salt, timing-insensitive `===` compare — no need for a constant-time compare given the "not real security" framing and the fact that a timing side-channel on a 4-digit local PIN check is a purely theoretical concern here), `clearPin()` (the "forgot PIN" clear, resets all three fields, saves). `hasLiveInputRisk()` (`sync.js`) gains `if (state.pinSetupActive) return true;`.

**Verify**: unit tests in `tests/applock.test.js` — `hashPin` is deterministic for the same salt+PIN, differs for a different salt (confirms salting actually changes the hash), `setPin`→`verifyPin` round-trips correctly for the right PIN and rejects a wrong one, `clearPin` resets all three fields to their off state.

### Stage 2 — Settings "Security" section
New `settings-nav-item` (`shield` icon, already in `icons/sprite.svg` — no sprite edit needed) alongside Display/Sync/Budgets/etc., `state.settingsActiveSection === "security"`. New section body: the "Require PIN" `.switch` toggle (same component as Dark mode's/Bill reminders' existing switches). Toggling on sets `state.pinSetupActive = true` and reveals two 4-digit numeric inputs (PIN, confirm) plus a Save button inline in the same row-area, following Categories' inline-form precedent — Save validates both fields match and are 4 digits, calls `setPin()`, clears `pinSetupActive`, shows a toast. Toggling off (only available once a PIN is already set) calls `clearPin()` immediately, no confirmation step and no PIN re-entry, and shows a toast with Undo per the decision above.

**Verify**: unit tests can't reach this (screen/DOM code, same reason `categoryFormHtml`/`saveCategoryForm` have none) — live-verified in a browser: enabling the toggle reveals the inline PIN+confirm fields; mismatched PIN/confirm blocks save with a toast; a valid 4-digit PIN saves and the toggle shows on; reloading the page (no lock screen built yet this stage, so this only confirms persistence) still shows the toggle on after reload; turning off immediately clears the PIN (toggle shows off) and the resulting toast's Undo restores it (toggle shows on again, same PIN works).

### Stage 3 — the lock screen overlay + boot gate
New empty `<div id="appLockContainer"></div>` in `index.html`, matching `#addSheetContainer`/`#manageSheetContainer`'s placement/reasoning. `applock.js` gains the render/wire functions: a full-screen `.filter-sheet-backdrop`-style overlay (no grabber, no drag-to-dismiss, no Escape listener — see the precedent section above) with a 4-digit PIN entry, an error state for a wrong attempt (clears the entry, brief shake, no lockout), and a "Forgot PIN?" link that calls `clearPin()` and unlocks immediately, same act-then-undo toast as Stage 2's toggle-off (the toast has to render somewhere still visible right after unlocking -- `#toast` is a top-level element in `index.html`, independent of both `#screen` and `#appLockContainer`, so it's unaffected by which of those is currently showing).

`main.js` boot sequence: after `loadFromStorage()` (so `pinEnabled`/`pinHash`/`pinSalt` are populated) and before the first `renderScreen()` call, if `state.pinEnabled` is true, render the lock overlay instead of proceeding — the first `renderScreen()` (and everything currently sequenced after it in boot: bill-notification deep-linking, `refreshIcons()`) only runs once the correct PIN is entered. A new `document.addEventListener("visibilitychange", ...)` (separate from `main.js`'s existing sync-on-visible listener — multiple listeners on the same event are fine, no conflict) does two things on `hidden`: applies the CSS blur/cover class immediately (decision 2), and — only if `state.pinEnabled` — sets the in-memory `locked` flag; on `visible`, if `locked` is true, shows the lock overlay again (gating the same way cold-load does) instead of just removing the blur.

**Verify**: live-verified in a browser (this is boot/DOM/visibility logic, no unit-test path, same reasoning as every other screen in this codebase) — with a PIN set: reload shows the lock screen before any app content, correct PIN unlocks and reveals whatever tab/state was active; switching browser tabs away and back re-locks; the app-switcher-blur class is confirmed present the instant `visibilitychange` fires to hidden (checked via devtools, not just visually); "Forgot PIN?" clears the PIN and unlocks immediately, and Settings' Security section afterward correctly shows the toggle off, with the toast's Undo restoring the PIN and re-locking on next background/reload; Tab-cycling while locked never reaches the covered app behind it (focus trap). Also add a new `e2e/app-lock.spec.js` (Playwright): enable a PIN via Settings, reload, confirm the lock screen blocks the app, unlock with the correct PIN, confirm a wrong PIN is rejected without unlocking, confirm "Forgot PIN?" clears it — this suite runs fully offline/signed-out already (`e2e/fixtures.js`), and none of this feature touches the network, so no new fixture work should be needed.

## Explicitly out of scope

- **WebAuthn / biometric unlock.** Genuinely deferred as a possible follow-up, not built now — this spec's decisions above (immediate threshold, 4-digit PIN, no lockout) are all sized for "lightweight convenience lock," and WebAuthn's own complexity (platform authenticator availability checks, credential storage, a meaningfully different UX for "no PIN fallback if WebAuthn itself fails") is a bigger lift than fits alongside that framing. If it's picked up later, it would layer on top of this spec's PIN as an alternative unlock method, not replace it — the PIN stays as the guaranteed-available fallback on any device/browser.
- **Any server-side/Supabase involvement whatsoever.** The PIN, its salt, and the enabled flag never leave `localStorage`; Supabase RLS and the existing Google OAuth session are completely unmodified by this spec.
- **Real account recovery for a forgotten PIN.** "Forgot PIN?" is a local clear-and-reset, explicitly not password-reset-style recovery (no email, no server round-trip) — see the decision above.
- **A configurable idle threshold / grace period.** Decision 1 above locks this to "immediate" for v1; a future pass could add a Settings option for this if it turns out to matter in practice, but it's not being speculatively built now.
- **Attempt lockout, rate limiting, or any escalating friction on repeated wrong PINs.**
- **Cross-tab lock-state synchronization.**
