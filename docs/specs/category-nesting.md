# Spec: one level of category nesting (subcategories)

Status: **implemented and live-verified** — `parentId` support across `src/categories.js`, `src/derived.js`, `src/sync.js`, `src/screens/settings-categories.js`, `src/screens/add.js`, migration `supabase/migrations/20260902120000_category_parent_id.sql`; unit-tested (`tests/categories.test.js`) and e2e-tested (`e2e/category-nesting.spec.js`). Interviewed to find the real goal, then read the current codebase (`src/categories.js`, `src/screens/settings.js`'s category CRUD, `src/screens/add.js`'s category picker, `src/derived.js`'s `breakdownEntries`) and the completed `custom-categories.md` spec this builds directly on top of, before staging a build plan the same way that spec was staged.

## Goal

Let a category optionally have one parent category (e.g. "Groceries" under "Food"), matching the two-level category model in apps like ezbookkeeping.

The request started as "add nesting because ezbookkeeping has it." Interviewed to find the actual driver: not a specific reporting gap (no complaint that Insights can't answer "how much on Groceries specifically"), not that today's 16-27 categories feel unmanageably long — genuinely just wanting whereisit's category model to match a mental model the user is already used to from another app. That framing matters for scope: this is about adding the *structure*, not about maximizing reporting depth, which is why several decisions below default to "keep it simple" (roll-up donut, no toggle, one level only) rather than building every possible nested-category feature.

## Relationship to `custom-categories.md`

That spec (all 5 stages done and live-verified) gave every category a stable `id`, full CRUD including on built-ins, sync across devices via a `categories` table with a **composite `(id, user_id)` primary key** (deliberate, documented in `supabase/migrations/20260829060000_categories.sql` — built-in categories share the same id across every user's row), an icon picker, and a delete guard that blocks deleting an in-use category. This spec adds exactly one new field (`parentId`) on top of that model and follows the same patterns throughout rather than inventing new ones:

- Same migration-file numbering/comment style as the existing `supabase/migrations/*.sql` files.
- Same `wireInlineCrud`/`manageRowHtml`/`inlineForm` Settings pattern `custom-categories.md` stage 3 already used — no new UI pattern invented.
- Same delete-guard shape (`categoryUsageCount` → block with a toast naming the count) extended with one more blocking condition, not a second guard mechanism.
- Same `resolveCategoryId`/`categoryDisplayName` read-path helpers in `categories.js`/`derived.js`, extended rather than duplicated.

## Decisions (confirmed via interview)

1. **One level only.** A category whose own `parentId` is already set cannot itself be chosen as a parent for another category — no three-plus-level chains. Matches the request and ezbookkeeping's model exactly; keeps the picker, donut rollup, and cycle guard all simple.
2. **A parent category stays directly assignable to a transaction**, even after it has children. A transaction can be tagged "Food" directly (no specific subcategory) or "Food > Groceries" — the app never forces every transaction under a parent to pick a specific child.
3. **Add-screen category picker: flat list, subcategories indented under their parent** — not a two-step parent-then-child picker. Fewer taps, and it matches every other picker in this app already being a single flat `<select>` (budgets, bills, the existing category select itself).
4. **Insights' category donut: subcategory spend rolls up into the parent's slice.** A parent's slice total is its own direct transactions plus all its children's. No user-facing toggle to expand back into per-subcategory slices in this pass — deliberately deferred as a possible fast-follow rather than built now, since nothing in the interview surfaced a concrete need for it yet.
5. **Deleting a category with children is blocked**, using the exact same guard/toast mechanism as deleting an in-use category (`categoryUsageCount` in `settings.js`) — not auto-detached to top-level. One blocking mechanism, one mental model for the user: "remove what's using this first."
6. **Any category, including a built-in, can be given a parent** — consistent with `custom-categories.md`'s "full CRUD, not just additive" decision. Nothing in this feature carves out built-ins as protected from being nested or from becoming a parent.

## Decisions made without a direct question (flagged for review before building)

- **Parent and child must share the same `type` (income/expense).** Nesting an expense category under an income parent (or vice versa) isn't offered by the parent picker at all — every category-type-scoped consumer in the codebase today (budgets, bills, the Add screen's type tabs, `guessCategory`) already assumes a category's type never changes after creation, and a cross-type parent/child pair would break that assumption in the donut rollup and the picker grouping.
- **Depth-cap enforcement needs three checks in the parent picker, not two.** Corrected after a review pass caught that two checks alone still let a 3-level chain in: if a category already has a parent excluded from being *chosen as* a parent (check b) that only stops picking an existing *child* as a new parent — it does nothing to stop *re-parenting a category that itself already has children*. Without a third check, editing category A (which has child B) to give A a parent C produces `C → A → B`, three levels. The three checks: (a) a category can't be set as its own parent; (b) a category that already has a non-null `parentId` can't be offered as a parent choice (blocks picking an existing child as a new parent); (c) a category that itself has at least one non-deleted child can't be given a parent at all — its own parent-picker field is disabled/locked to "no parent" while it has children, same as decision 5's delete-block condition, one consistent rule: "a category with children must stay top-level." Combined with same-user, single-hop-only `parentId` reads elsewhere in the app (decision below on cross-device races), these three checks are sufficient because the only way to introduce a level beyond two is through one of exactly these three actions, and all three are now blocked at the picker.
- **The self-referencing FK is scoped `(parent_id, user_id) references categories(id, user_id)`**, not a plain `parent_id references categories(id)` — matching the existing composite-key shape so the database itself can't let one user's category parent-reference another user's row. Its `on delete restrict` clause is honest about being a narrow safety net, not the operative guard: `deleteCategory()` never issues a real SQL `DELETE` at all — like every delete in this app, it's a soft delete (`categoryToRow(c, true)` pushed with `deleted: true`), so the FK's restrict clause only ever matters against a direct, out-of-band hard delete (e.g. run manually against the database), never against normal app usage. The actual live guard against deleting a parent with children is the app-level `childrenOf(...).length > 0` check in stage 2, exactly like `categoryUsageCount` already is the live guard against deleting an in-use category — there's no FK enforcing *that* one either.
- **Two categories independently set as each other's parent from two different devices (a concurrent-edit race) is a known, accepted, low-severity gap, not something this spec re-engineers sync to prevent.** `mergeRowsById` resolves each row independently by its own `updatedAt` (`merge.js`) — it has no cross-row transaction and can't validate the resulting graph shape, so a same-user two-device race could theoretically produce `A.parentId = B` and `B.parentId = A` simultaneously. This is accepted for the same reason `dropPendingForRemovedIds`'s tombstone race is accepted elsewhere in this codebase: fixing it for real needs either a server-side constraint trigger or a multi-row transaction this app's sync model doesn't have, for a case an actual single user triggering two simultaneous edits on the same category pair, offline, on two devices, is very unlikely to hit. Impact is bounded and non-crashing by construction: every read path that walks `parentId` (`ancestorId`, the parent-picker's own eligibility filter) does exactly **one hop**, never a recursive walk, so a two-node cycle can't cause an infinite loop or a stack overflow anywhere — worst case is a confusing but stable display (both categories shown indented under each other) until the user (or a later edit) breaks the cycle by hand.
- **A parent soft-deleted while a child still references it (another concurrent-edit race, e.g. one device deletes a parent while another device is mid-edit adding a child to it) leaves the child's `parentId` pointing at a tombstoned row.** `ancestorId(list, id)` treats a `parentId` that doesn't resolve to a live (non-deleted) category the same as `null` — the child displays and behaves as top-level rather than erroring or vanishing, matching this codebase's established "never worse than before" fallback pattern (`resolveCategoryId`/`categoryDisplayName` already do exactly this for a category deleted out from under a transaction).
- **Budgets, bills, budget alerts, and unbudgeted-spend calculations (`computeBudgets`, `checkBudgetAlert`, `unbudgetedSpend`, etc. in `derived.js`) are explicitly NOT changed by this spec and keep treating a parent and its children as fully separate category ids**, never rolled up — only Insights' breakdown donut (stage 5) rolls up. A budget is inherently tied to one specific category a user chose (e.g. "Groceries" specifically, not "Food" in general), so rolling budget tracking up to the parent would silently change what a user's existing budget means. Flagging this explicitly (not just as an implied side effect of "only stage 5 touches `breakdownEntries`") since a reviewer could otherwise read stage 5's rollup and assume it applies everywhere spend-by-category is computed.
- **No bulk "convert existing category into a parent/child" migration UI.** Existing categories all start with `parentId: null` (flat, exactly like today) after this ships; nesting is opt-in per category via editing it in Settings, not something applied retroactively by the app.
- **Settings' category list groups children directly under their parent visually** (indented rows, parent immediately followed by its children, otherwise preserving today's existing array order — categories are never actually sorted by the `sortOrder` field despite its name, it's only set at creation and never read back) rather than a collapsible tree — matches this app's existing preference for flat scannable lists (see `manageRowHtml`'s existing swipe-row pattern) over disclosure widgets, and avoids yet another `state.settingsGroupOpen`-style piece of transient UI state.

## Staged build plan

### Stage 1 — migration + sync plumbing (additive, no behavior change yet)
New nullable `parent_id text` column on `public.categories`, migration file following the existing numbering convention (`supabase/migrations/<timestamp>_category_parent_id.sql`). Self-referencing composite FK: `foreign key (parent_id, user_id) references public.categories(id, user_id) on delete restrict` — see the decision above on what this `restrict` clause does and doesn't actually guard (a narrow safety net against a direct hard delete, not the live app-level guard, since this app only ever soft-deletes). RLS unchanged (existing single `ALL` policy already covers the new column; no new policy needed).

`categories.js`: add `parentId` to whatever shape flows through `categoryToRow`/`rowToCategory` (`sync.js`) and `mergeRowsById`'s pass-through fields (`merge.js` doesn't need logic changes, just confirm the new field round-trips). New pure helpers: `topLevelCategories(list)`, `childrenOf(list, parentId)`, `isParentCategory(list, id)` (has at least one non-deleted child), `ancestorId(list, id)` (returns the category's own id if top-level or if its `parentId` doesn't resolve to a live category, else its `parentId` — this is both the "roll up to depth 1" helper stage 4 needs and the orphaned-child fallback described above). Note `sortOrder` (`categories.js`/`sync.js`) is already read today, just not where this spec originally assumed — `mostUsedCategoryIds` (`derived.js`) uses it as the tiebreak/padding order for the Add screen's quick-pick chips; it's `categoryRowHtml`'s Settings *list* rendering specifically that never sorts by it (plain array order there).

**Verify**: sign in on two devices, set a parent on a category on device A, confirm `parentId` and the correct grouping appear on device B after sync; a local-only (never signed in) user can still set/clear a parent with zero network calls.

### Stage 2 — cycle/depth guard + delete guard
`categoryFormHtml`'s new parent-picker `<select>` (see stage 3) only ever lists candidate parents that (a) match the being-edited category's `type`, (b) aren't the category itself, (c) don't already have a `parentId` set (blocks picking an existing child as a new parent) — built as a pure, testable filter function in `categories.js` (e.g. `eligibleParentOptions(list, editingId, type)`) rather than inline DOM logic, so it can get unit test coverage. A fourth, separate check gates the *field itself* rather than filtering its options: `isParentCategory(list, editingId)` (has at least one non-deleted child) — if true, the parent picker is disabled/hidden entirely and forced to "no parent," since a category with children must stay top-level (see the corrected depth-cap decision above). Together, (a)-(d) are what actually close the 3-level-chain gap a first-draft two-check version of this filter missed.

`deleteCategory` (`settings.js`) gains one more blocking condition alongside the existing `categoryUsageCount(id) > 0` check: `childrenOf(categories, id).length > 0` also blocks, with its own toast text naming the child count (reusing the existing toast-with-count pattern, new string key).

**Verify** (unit tests in `tests/categories.test.js`, new file — this module has none yet despite being pure): `eligibleParentOptions` correctly excludes a category that already has a parent, excludes the category being edited itself, excludes cross-type categories, and returns everything else; `isParentCategory` correctly identifies a category with children (so its own parent field would be locked); `childrenOf`/`isParentCategory` return correct results including the zero-children case; a regression test specifically for the caught gap — a category with an existing child is never returned by `eligibleParentOptions` when picking a parent *for that same category* (i.e. attempting to re-parent a parent-with-children is rejected).

### Stage 3 — Settings category management UI
`categoryFormHtml` (`settings.js`) gains a new field: a parent-category `<select>` (using `eligibleParentOptions`, `optionsHtml`'s existing helper), defaulting to "no parent" (a top-level category), positioned after the icon picker. Unlike `type` (locked after creation), the parent stays editable on an existing childless category at any time — re-parenting or promoting a subcategory back to top-level are both just this one field changing, no special-cased flow. If the category being edited has children (`isParentCategory` from stage 2), the field renders disabled with an explanatory note instead (matching this app's existing pattern of disabling rather than hiding a field that has a reason attached, e.g. the Add screen's `required`-toggling precedent) — the user must first re-parent or remove its children before this category itself can be nested under something else.

`categoryRowHtml`'s list rendering (currently `categories.map(categoryRowHtml).join("")`, rendered in plain array order — despite the `sortOrder` field's name, nothing in the codebase actually sorts by it today, it's only ever set at creation time and never read back for ordering) changes to a stable sort that groups children immediately after their parent while otherwise preserving today's existing array order, and `categoryRowHtml` itself gets an `isChild` flag that adds an indent (reusing `manage-row`'s existing CSS rather than a new component) so the grouping reads visually as a tree without an actual collapsible widget.

**Verify**: creating a category with a parent selected shows it correctly indented under that parent in the list; editing an existing category to add/remove/change its parent immediately re-groups the list; attempting to delete a category that has children is blocked with an accurate count in the toast; attempting to delete an in-use childless category still works exactly as before (regression check on stage 3 of `custom-categories.md`'s existing guard).

### Stage 4 — Add screen category picker
`renderFormCategoryOptions` (`add.js`) switches its option list from a flat `categories.filter((c) => c.type === state.formType)` to that same list re-sorted so every child immediately follows its parent, with each child's label prefixed by an indent (e.g. two non-breaking spaces) via a new `labelFn` passed to `optionsHtml` — a native `<select>` still shows one flat option list, so indentation via the label text is what actually delivers "flat, indented" (decision 3) rather than `<optgroup>`, which can't also make the group's own label independently selectable and Food itself must stay selectable per decision 2.

The category-chip quick-picker (`renderCategoryChips`, `docs/specs/category-icon-chips.md`) is unaffected in structure — `mostUsedCategoryIds` already surfaces whatever a user actually taps most, parent or child alike, and the "more" fallback opens the same `<select>` this stage changes.

**Verify**: adding/editing a transaction shows subcategories correctly indented under their parent in the select, in the correct grouped order; selecting a parent category directly still works; selecting a subcategory still auto-fills its icon/chip correctly; a category with no parent (today's normal case) renders identically to before this stage.

### Stage 5 — Insights donut rollup
`breakdownEntries` (`derived.js`) changes its aggregation key from `resolveCategoryId(t, "expense") || t.category` to running that result through the new `ancestorId(categories, cid)` helper from stage 1 before accumulating into `totals`/`names` — a subcategory's spend lands in its parent's bucket, and the displayed name resolves to the parent's (`breakdownEntries` today returns no icon field at all — `insights.js`'s breakdown row renders a colored legend dot, not an icon, so there's nothing icon-related for this stage to change). No change to `breakdownEntries`' signature, callers, or the existing top-6-slices/`categoryIds`-pre-filter behavior (`docs/specs/transactions-filters-rework.md`) — filtering by a specific subcategory still filters at the transaction level before rollup, so picking "Groceries" in a filter still shows only Groceries' own transactions even though the unfiltered donut would have shown it merged into Food.

**Verify** (unit test in `tests/derived.test.js`, alongside the existing `computeBreakdown` coverage from `custom-categories.md` stage 2): a transaction tagged with a subcategory and another tagged with its parent directly both land in one combined slice under the parent's name/total; a transaction under a category with no parent behaves exactly as today (regression check). Live-verified in a browser: create a subcategory, add a transaction under it, confirm Insights' breakdown shows it merged into the parent's slice/total, not as a separate row.

## Explicitly out of scope

- More than one level of nesting.
- A toggle to expand the donut back into per-subcategory slices (decision 4) — possible fast-follow, not this pass.
- Auto-detaching a parent's children on delete instead of blocking (decision 5).
- Bulk/retroactive re-nesting tooling — every category starts flat; nesting is opt-in per category via the edit form.
- Any change to `guessCategory`/`CATEGORY_KEYWORDS`' matching behavior — auto-guess keeps resolving directly to whatever id it already resolves to today (parent or child), unaffected by nesting.
- Server-side/transactional protection against the two concurrent-edit races documented above (a two-device mutual-parent cycle; a child's parent soft-deleted mid-edit on another device) — accepted as low-severity, bounded-impact gaps consistent with other documented sync races in this codebase, not solved with new sync infrastructure in this pass.
- Rolling budgets/bills/budget-alerts up to a parent category — only Insights' breakdown donut rolls up (stage 5); every other spend-by-category computation keeps treating parent and child as fully separate ids.
