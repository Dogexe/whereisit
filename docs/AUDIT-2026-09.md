# Product audit — September 2026

Point-in-time findings against build `413bf37` (clean tree), verified in a
real browser against the local `dist/` build; two findings re-confirmed
against the deployed site. Baseline at time of audit: 173/173 unit, 32/32
e2e, all green.

**This file ages. It records what was true on 2026-09-08, not what is true
now.** Before acting on any finding, re-verify it against current code —
some will have been fixed. `docs/ROADMAP.md` owns what is planned and what
has moved; this file owns the evidence behind each finding. Presentation
copy: https://claude.ai/code/artifact/4a8fd7c9-d010-4f2b-bedd-cefc5f7389e3

Evidence is tagged: **[V]** reproduced by driving the running app;
**[C]** read from source with no runtime reproduction; **[R]** competitor
research from a vendor's own current store listing.

Items already in `docs/UX.md`'s "Known UI debt" were confirmed present but
deliberately **not** re-reported here — that stream keeps its own ownership.

## Defects

### D1 — Fresh install seeds four bills and four budgets as the user's own data
Critical · confidence high · **[V]**, incl. the deployed site.

`src/state.js:121-132`. On a never-touched profile, Home renders
"ค่าเช่าห้อง · เกินกำหนด 7 วัน · ฿8,000.00" with a live "จ่ายเลย" button, plus
฿590 internet, ฿1,200 health insurance, ฿349 Netflix, and four budgets
totalling ฿6,500. Insights reports "฿0.00 / ฿6,500.00". Written to
`expense_tracker_settings_v1` on first save, so they also form the first sync
payload; a signed-in user's *new device* gets them merged alongside real rows.

Reference **[R]**: Money Manager (Realbyte) opens with no entries and
contextual tips. Default scaffolding — categories, an account — is the
category norm; fabricated obligations with amounts and overdue states are not.

**Status: specified.** `docs/specs/first-run-empty-defaults.md`, ticket
`WI-023`. Note removal exposes two missing empty states — see that spec.

### D2 — "Mark paid" is irreversible
Critical · confidence high · **[V]**, incl. the deployed site.

`src/screens/home.js:32-56` (`markBillPaid`), wired at `home.js:292`. One
click took transaction count 0 → 1 and wrote
`{type:"expense", amount:8000, note:"ค่าเช่าห้อง"}`. Toast read "เพิ่มรายการแล้ว"
with **zero** undo buttons. The same call sets `bill.lastPaidCycle`, which
`grep` confirms is written in exactly one place and cleared in none — the bill
edit form (`settings-bills.js:52`) mutates fields in place and leaves it
untouched. There is no UI path to un-mark a bill for the current cycle.

The pattern already exists two files away: `deleteBill`
(`settings-bills.js:70`) passes an undo callback to `showToast`, and
`docs/UX.md` states "Undo over confirm."

### D3 — Back exits the app and discards an open Add sheet
High · confidence high · **[V]**, incl. the deployed site.

`src/screens/router.js:16` (`setTab` mutates state and re-renders, pushing no
history). Pixel 7: `history.length` stayed at 2 across Home → Transactions →
Insights; opening the Add sheet did not change it; `goBack()` with the sheet
open navigated to `about:blank`. Only `settingsSubPage` is history-backed
(`settings.js:161`).

`settings.js:170`'s `popstate` listener does **not** inspect `event.state`.
Sheet-by-sheet co-open analysis is in `docs/ROADMAP.md`'s WS-3 section — five
of six sheets never co-open with a Settings sub-page; only Manage does.

### D4 — English translates chrome but not content
High · confidence high · **[V]**.

`src/state.js` and `src/categories.js` store category, account, budget and
bill names as literal Thai strings; `categoryDisplayName`
(`categories.js:104`) returns the stored string with no language branch. With
`lang: "en"`, Home reads "Total balance / **เงินสด**", "Upcoming bills /
**ค่าเช่าห้อง**"; the Add form reads "Category" above a chip row of
**อาหารและเครื่องดื่ม · การเดินทาง · ที่อยู่อาศัย/ค่าเช่า · …**

Not simply "translate the seeds": a user-renamed category must keep its
chosen name, so built-ins need a translation key alongside the stored name
plus a rule for which wins. Blocked on the English-scope decision
(`docs/ROADMAP.md`).

### D5 — Persistent storage is never requested
High · confidence medium · **[C]**.

Repo-wide grep across `src/` and `sw.js` for `navigator.storage`,
`storage.persist`, `indexedDB` returns nothing. `docs/SOT.md` states
`localStorage` is the source of truth and sign-in is optional, so for an
unsigned user it is the only copy. Measured payload: **357 KB at 2 000
transactions**, ~28 000 before the ~5 MB quota — quota is not the risk,
eviction is. Confidence is medium because eviction is browser- and
pressure-dependent and was not forced; what is verified is the absence of any
mitigation.

### D6 — Transaction list renders every row
High · confidence high · **[V]**, measured.

`src/screens/transactions.js:230-244` (`renderTxListOnly`), called from the
search `input` handler at `transactions.js:385`. Seeded 2 000 transactions,
desktop Chrome 1280×900:

- First render of the Transactions tab: **1 474 ms**, **2 000** `.tx-row-wrap`
  elements in the DOM. No pagination, no virtualisation, no cap.
- One `input` event leaving ~2 000 rows matched: **726 ms** of blocking
  main-thread work, measured in-page with `performance.now()` around dispatch.
- Next keystroke, narrowing to ~1 100 rows: **367 ms**.

2 000 transactions is roughly two years at three a day. These are desktop
numbers; the mobile shell is the primary target.

### D7 — Amounts with >2 decimals are rejected by an untranslated dialog
Medium · confidence high · **[V]**.

`src/screens/add.js:317` — `<input type="number" step="0.01">`. Typing
`10.555` gives `{valid:false, stepMismatch:true, validationMessage:"Please
enter a valid value. The two nearest valid values are 10.55 and 10.56."}` and
`form.checkValidity() === false`. Native validation blocks the submit before
the handler at `add.js:456` runs, so the app's localised `toastInvalidAmount`
never fires. Same `step="0.01"` on the bill, budget and goal amount inputs.

Same class as the hidden-`required` Transfer-tab bug already recorded in
`docs/ARCHITECTURE.md`: native validation intercepting a submit with no
app-visible signal.

### D8 — Nav state and toasts are invisible to assistive tech
Medium · confidence high · **[V]**.

Read back from the running page:

- `aria-current` is `null` on all ten nav buttons; active state is a CSS class
  only (`router.js:67`).
- `#toast` has `role: null, aria-live: null` (`index.html:91`) — "transaction
  added", "budget exceeded", "save failed" and every undo prompt announce to
  nobody. The Add sheet's commit preview *does* carry `aria-live="polite"`, so
  this is an inconsistency, not an unknown pattern.
- Zero `<h1>` on any screen; every screen title is an `<h2>`.
- Both `<nav>` landmarks unlabelled; no skip link past the five nav buttons.

The undo toast is the app's only safety net for destructive actions, and a
screen-reader user never learns it exists. This is also a gap in the design
system: `docs/UX.md`'s Accessibility section covers accessible names and focus
indicators but says nothing about conveying current state or announcing status.

### D9 — `docs/SYNC.md` documents a function that no longer exists
Low · confidence high · **[V]**.

`docs/SYNC.md:31` still says `merge.js` has `mergeBudgetsByCategory` and that
it "preserves a documented pre-existing quirk, not a bug to 'fix'". It was
removed during the custom-categories work — `merge.js:21-32` and
`sync.js:421` both carry comments explaining the removal. This is the only
stale claim found across the whole doc set.

## UX weaknesses

- **U1** — the Add sheet opens with focus on Cancel, so the keypad never
  appears. `utils.js:213-221`: `createFocusTrap().activate()` focuses the
  first focusable in DOM order, which is the header's Cancel button. Entry
  speed decides whether a manual tracker survives past week two, and the
  sheet's own layout already puts the amount first and largest. **[V]**
- **U2** — the Trend chart cannot be read. `insights.js` ~line 330. At 1280px
  with 2 000 transactions: six pairs of ~10px bars in a 990px card, no y-axis,
  no gridlines, no value labels, no hover targets, fixed six-month period
  while the sibling tabs both have a full period picker. **[V]**
- **U3** — filtering never shows the filtered total. `transactions.js:353-376`
  renders title, toolbar, chips, list — no count, no sum. The filter machinery
  (type, period, multi-category, multi-account, amount range, search, chips,
  count badge) is better than the comparators'; it just never states its
  answer. **[V]**
- **U4** — future-dated entries join the balance silently. `#txDateNative` has
  no `max`; `computeBalance`/`byRecency` have no date ceiling. A ฿50 expense
  dated 2099-12-31 saved without warning; Home then showed total balance
  `฿-57.00` while both month cards read `฿0.00`, with the 2099 row pinned to
  the top of Recent activity as `31/12/2642`. Dates in 1900 accepted too. **[V]**
- **U5** — the Insights segmented control spans ~990px at 1280px, active pill
  floating mid-track with the outer labels pinned to the edges. Correct at
  mobile width, so it is desktop-only stretch. Partly subjective. **[V]**

## Competitive gaps

Comparators chosen for workflow similarity — manual entry, multi-account,
category budgets, offline-capable, individual rather than household:
**Money Manager (Realbyte)**, **Monefy**, **Wallet (BudgetBakers)**, **Money
Lover**, **Bluecoins**. Bank-aggregation-first products and envelope-budgeting
systems were excluded as a different job. All five are native mobile;
whereisit is the only PWA, which is a differentiator rather than a shortfall.

- **C1** — no in-app keypad or calculator; the amount field is a bare
  `type="number"` on the OS keyboard. Monefy ships a calculator as a headline
  feature; Money Manager lists "search and calculator functions". **[R]**
- **C2** — no recurring transactions. A bill has `name`, `amount`, `day`,
  `category`, `lastPaidCycle`; `nextBillDueDate` (`derived.js:211`) is
  monthly-only with no frequency field, and nothing is created automatically.
  Month-end clamping is correct. Money Manager offers "automatic money
  transfer and frequency functions" plus payment profiles. Weekly,
  fortnightly, quarterly and annual bills cannot be represented at all. **[C][R]**
- **C3** — no way to erase everything. Swept every rendered button across
  Settings and its sub-pages for a reset/erase/clear affordance: zero matches.
  The only wipe path is `wipeLocalAccountData()`, which fires on sign-out or
  account switch and is not user-invocable. **[V]**
- **C4** — currency hardcoded. `utils.js:38` hardcodes the `฿` prefix; the
  locale switches `th-TH`/`en-US` for digit grouping but the symbol never
  does. All five comparators support multiple currencies. **[V][R]**

## Engineering risk

- **F1** — `src/sync.js` (620 lines, the largest module) has no automated
  coverage. `tests/` covers every *pure* piece sync depends on — `merge`,
  `pending`, `watermark`, `paginate`, `account`, `derived`, `utils`, `import`,
  `applock`, `categories`, `restore` — but there is no `sync.test.js`. The
  orchestration itself is untested: `syncNow`'s pull-then-push ordering, the
  `syncEpoch` guard, `markAllPending` on genuine sign-in, chunked push failure
  handling, `dropPendingForRemovedIds`. `docs/TESTING.md` confirms the e2e
  suite runs fully offline and signed-out, so no spec exercises a signed-in
  state either. The well-tested helpers make the untested seam *read* as
  covered, which is how this gap stays forgotten. **[V]**

### Do not copy from competitors

- **Bank aggregation** — the biggest driver of paywalls, permission friction
  and support burden in the category, and it contradicts a local-first product
  that works with no account.
- **Ads / free-paid split** — Money Manager and Monefy both monetise this way.
  Free, ad-free and account-optional is a real differentiator.
- **Feature maximalism** — Money Manager ships double-entry bookkeeping, payee
  statistics, a Wi-Fi desktop manager. This product's clarity is its advantage.
- **Auto-generated recurring transactions** — if C2 is built, keep the
  reminder-plus-confirm model. D2 is a small demonstration of why unconfirmed
  generated financial rows are a bad idea.

### Already competitive or deliberately different

Sync engineering (keyset pagination, per-table watermarks using `.gte`,
persisted chunked pending queue, soft deletes, `syncEpoch` guard, RLS verified
per table, composite FKs scoped to `user_id`) · Thai as a first-class language
with correct Buddhist-era conversion both directions · the mobile Add sheet's
design (amount hero, live commit preview, Cancel/Save outside the scrollport,
correct `visualViewport` handling) · the desktop shell · transfers as one row
with `account_id`/`to_account_id` · local-first with optional sync ·
documentation honesty, including a consciously-shipped contrast failure with
its reasoning recorded.

## Checked and found sound

Recorded so these are not re-audited:

- No unescaped interpolation of user-supplied names, notes or categories
  anywhere in `src/` — scanned every template interpolation.
- The offline app shell loads with the network cut.
- Bill due-date month-end clamping is correct (`derived.js:211-221`).
- The hide-amounts toggle masks percentages as well as figures.
- Delete-with-undo works on both transactions and bills.
- Buddhist-era date conversion is correct in both directions.
- Corrupt storage is caught and ignored rather than crashing the boot.
- Unit tests build their own fixtures and do not depend on `state.js` seeds.
- Both test suites pass from a clean tree.
