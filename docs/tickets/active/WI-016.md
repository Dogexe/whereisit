# WI-016 — Expense amounts render red

Status: Ready

Spec: `docs/specs/amount-color-semantics.md`

Codex profile: terra-medium

## Goal

Expense transaction amounts render in the existing `--color-expense-700`
red instead of neutral text color, matching a fintech-standard convention
(red negative / green positive) the user asked to adopt. Income keeps its
existing green; transfer rows are unaffected.

## Acceptance criteria

- [ ] `src/screens/tx-row.js`'s non-transfer amount color (currently `type
      === "income" ? "var(--color-income-700)" : "var(--color-text)"`,
      around line 72) uses `--color-expense-700` for expense instead of
      `--color-text`.
- [ ] `src/screens/add.js`'s commit-preview amount color (same pattern,
      around line 229) gets the identical change.
- [ ] Income amounts are pixel-identical to before (still
      `--color-income-700`).
- [ ] Transfer row amounts (`tx-row.js`'s transfer branch, ~lines 35-47)
      are pixel-identical to before — untouched.
- [ ] `docs/UX.md`'s "Amount coloring" bullet (under "Color semantics") is
      rewritten to state the new rule and no longer says "a normal expense
      is never red."
- [ ] Existing related behavior remains unchanged.

- New design primitives required by this ticket: none.

  the Type control changes.
- Desktop (>=1024px) behavior: same, via the desktop full-page Add/Edit
  form (shares `renderCommitPreview()` with the mobile sheet).

## Implementation guidance

- Likely files: `src/screens/tx-row.js`, `src/screens/add.js`,
  `docs/UX.md`.
- Likely functions: `txRowHtml()` (`tx-row.js`), `renderCommitPreview()`
  (`add.js`).
- Existing pattern to reuse: both files already use the exact ternary
  shape `type === "income" ? "var(--color-income-700)" : "var(--color-text)"`
  — change only the `: "var(--color-text)"` fallback to
  `: "var(--color-expense-700)"` at each site. Both ternaries are only ever
  evaluated for `income`/`expense` (transfer is handled by an earlier
  branch/return in each file), so this is a safe two-value swap, not a
  three-way rewrite.
- Relevant tests: check for any existing unit/e2e assertions on amount
  color/class before adding new ones; add a narrow e2e check if none
  exists that would catch a regression here.
- Known invariants: transfer rows must stay neutral — do not touch
  `tx-row.js`'s transfer branch.
- Do not change: `--color-expense-700`/`--color-income-700`'s hex values
  (that's WI-017/WI-018's concern), avatar/icon colors, any non-amount
  text color.
- Escalate back to Claude if: a third call site rendering an
  income/expense amount turns up that wasn't listed here (the spec's grep
  found only these two plus two confirmed-unaffected spots — `home.js`
  stat-card deltas and `settings-goals.js`'s goal progress bar).

- **Confirmed defect:** re-ran `npm run test:e2e` independently and the new
  test ("expense, income, and transfer amounts keep their semantic colors")
  failed deterministically — not the Chromium-environment flake noted
  above. Root cause: the test calls `createAccount()` before checking the
  Appearance toggle; `createAccount()` navigates desktop Settings to the
  Accounts section, which sets `state.settingsSubPage = "accounts"`
  (`settings.js:429`) and that persists across screens. The later
  `navBtn(page, "settings").click()` therefore lands back on the Accounts
  panel, not Display, so the Appearance disclosure trigger exists in the
  DOM but isn't visible, and the click times out.
- **Fix (Codex, same round):** the test now calls
  `openSettingsSection(page, "display")` (existing helper) right after
  navigating to Settings and before opening Appearance, so it explicitly
  returns to the Display section regardless of what a prior helper left
  active.
