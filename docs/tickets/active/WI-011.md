# WI-011 — Settings sub-page chrome: hidden tab bar and Add FAB

Status: Ready

Spec: `docs/specs/settings-chatgpt-style-navigation.md` (decisions 9
and 10)

Codex profile: terra-medium

Profile reason: bounded presentation/chrome work with a settled shape.
It touches no state model and no history handling — `WI-008` already
owns those and is shipped. The one genuinely fiddly part (every element
anchored "above the tab bar" agreeing on its height) is mechanical once
found, and `styles.css` already documents where those offsets live.

## Goal

While a Settings sub-page is open below 1024px, hide the bottom tab bar
so the back arrow is the only way out, and render that section's
existing Add button as a floating action button in the bottom-right
instead of a `+` in the sub-page header.

**Chrome only.** No change to `state.settingsSubPage`, to the
`pushState`/`popstate` handling `WI-008` shipped, or to what any Add
button does when pressed.

## Acceptance criteria

- [ ] Below 1024px with a sub-page open, `.tabbar-wrap` is not visible.
      It returns as soon as the sub-page closes by any route: the back
      arrow, the hardware/browser Back button, or a `popstate` from any
      other source.
- [ ] The tab bar's visibility is driven off the same
      `state.settingsSubPage` field `WI-008` established — no second
      state field, and no direct `.style.display` writes left behind on
      the element after it is shown again.
- [ ] Every offset that today assumes the tab bar's height collapses to
      the bare `env(safe-area-inset-bottom)` while a sub-page is open,
      and is restored afterwards. `styles.css`'s tab-bar comment names
      these: `.screen`'s `padding-bottom` and `#toast`'s bottom offset.
      Re-grep for `--tabbar-h` rather than trusting that list.
- [ ] **The Undo toast raised by deleting a Manage row is fully visible
      on a sub-page**, not floating in the dead space where the tab bar
      used to be. This is the concrete reason the previous criterion
      exists — deletes happen on sub-pages.
- [ ] The section's Add button (`addBudgetBtn`, `addBillBtn`,
      `addGoalBtn`, `addCategoryBtn`, `addAccountBtn`) renders once, as
      a bottom-right FAB. The same element id and click behavior are
      kept so `wireInlineCrud` and `renderManageSheet` need no change.
      No `+` remains in the sub-page header.
- [ ] The sub-page header keeps its back arrow and section title, and
      stays a single row.
- [ ] The FAB clears the last row instead of covering it: the sub-page's
      scrollable content ends with enough bottom padding that the last
      row can be scrolled clear of the FAB.
- [ ] The FAB does not overlap a `WI-005` swipe row's revealed action
      buttons in a way that makes any of them unreachable. Verified by
      swiping the **last** row in a sub-page open, since that is the
      only row the FAB can reach.
- [ ] `manage-row-swipe.js`, `tx-row.js`, `renderManageSheet`,
      `wireInlineCrud`, and the six `xFormHtml()` modules are not
      modified.
- [ ] The Security sub-page, which has no Add button, renders no FAB and
      still hides the tab bar.
- [ ] At 1024px and up nothing changes: `.tabbar-wrap` is already
      `display: none` there, no FAB is rendered, and the desktop
      master–detail panes keep their existing inline Add buttons in
      place.
- [ ] The FAB's size, radius, color and shadow come from existing
      `--space-*` / `--radius-*` / color tokens and the app's existing
      button primitives. No new spacing, radius or color values.
- [ ] The FAB has an accessible name (reuse the existing Add button's
      `aria-label`) and a touch target of at least 44px.
- [ ] Light and dark mode both render correctly.
- [ ] e2e coverage: on a mobile viewport, drill into a Manage sub-page
      and assert the tab bar is hidden and the FAB is visible; close the
      sub-page and assert the tab bar is back. Existing specs that click
      an `addXBtn` inside a sub-page must still pass unchanged.

## Verification

- [ ] `npm test`

- [ ] `npm run build`
- [ ] Real-browser checks against a served `dist/` build at a mobile
      viewport, in **both** themes:
      1. Drill into each of the five Manage sub-pages and Security:

      4. Scroll to the bottom of a long sub-page (Categories) and

      5. Leave a sub-page with the hardware/browser Back button and
         confirm the tab bar returns.
- [ ] Confirm at 1280px that nothing changed.
- [ ] Complete diff inspected for unrelated changes.

## Out of scope

- Any change to the navigation model, history handling, or
  `state.settingsSubPage`'s meaning (`WI-008`, shipped).
- The root list's visual language, the profile header, the Log out row,
  the Privacy policy row and the section grouping/order (`WI-009`).
- Expand-in-place Appearance / Accent color / Language rows (`WI-010`).
- Hiding the tab bar anywhere other than a Settings sub-page. The Add
  screen, the bottom sheets and every other screen keep it.
- Any schema, storage, or sync change.

## Dependencies

`WI-009` should land first. This ticket positions the FAB and the
sub-page header against the card metrics `WI-009` sets; doing it first
means tuning those offsets twice.
