## Goal

A bill can be un-marked from Home after its undo toast is gone, and the row's
actions move into the same swipe treatment the rest of the app uses instead of
Home's bespoke inline pill.

## Acceptance criteria

- [ ] Home's bill row renders through `manageRowHtml()`
      (`manage-row.js:49-65`), so it swipes below 1024px and renders the same
      action inline as `.row-actions` at 1024px+, with no second
      implementation and no viewport branch written in `home.js`.
- [ ] The row exposes exactly **one** action in this ticket, whose identity
      follows row state: **Mark paid** on an unpaid row, **Un-mark** on a paid
      one. No Edit, no Delete.
- [ ] The `.btn-sm` pill (`home.js:280`) is removed, and
      `[data-mark-paid]`'s existing wiring (`home.js:305`) keeps working from
      its new home.
- [ ] `unmarkBillPaid(id)` is added in `home.js` beside `markBillPaid()`. It
      clears `lastPaidCycle`, stamps `updatedAt`, `saveSettings()`, re-renders,
      and pushes via `pushRows("bills", [billToRow(bill, false)])` then
      `syncNow()` — the shape `toggleArchiveAccount()`
      (`settings-accounts.js:103-116`) already uses.
- [ ] **Un-mark does not touch any transaction.** It clears the bill's cycle
      only. Its toast says the bill was un-marked, not that anything was
      undone — see Implementation guidance for why this is not negotiable.
- [ ] `markBillPaid()`'s existing 4-second undo toast (`home.js:57-69`) is
      **unchanged** and still reverses both halves within its window.
- [ ] Un-marking a bill returns it to its unpaid presentation: the paid state
      word and modifier class from `WI-030` come off, and the row reads as due
      or overdue again.
- [ ] The swipe is wired on Home. `wireManageRowSwipe($("screen"))` is called
      from Home's wiring pass guarded by `!isDesktopShell()`, exactly as
      `settings.js:516` does it.
- [ ] No action on this row takes Delete's full-swipe-to-commit gesture.
      Nothing here is destructive; every action is one tap to reverse.
- [ ] Two new `STRINGS` keys at most: the Un-mark `aria-label` and its toast.
      Reuse `markPaidBtn` (`i18n.js:114`) for the Mark action.
- [ ] Settings' Manage rows, transaction rows, and every other swipe surface
      are visually and behaviourally unchanged.

## UX / design references

- Follow `docs/UX.md`.
- Match existing: Accounts' swipe row (`settings-accounts.js:20-29`) — same
  circle geometry, and the same conditional `aria-label` pattern where one
  button's label flips on record state.
- Reuse: `manageRowHtml`, `manageSwipeWrapHtml`, `wireManageRowSwipe`,
  `showToast`, `billToRow`, `pushRows`.
- New design primitives required by this ticket: none.
- Mobile (<1024px) behavior: swipe left to reveal one circle.
- Desktop (>=1024px) behavior: the same action inline in `.row-actions`, which
  is what `manageRowHtml` does above the breakpoint. The feature must not
  become mobile-only.

## Implementation guidance

- **Likely files:** `src/screens/home.js` (row markup `:270-283`, wiring
  `:299-307`, new mutator beside `markBillPaid` at `:32`), `src/i18n.js`,
  possibly `styles.css` for the new circle's tone.
- **Why un-mark cannot delete the expense.** `markBillPaid()` creates a
  transaction with no link back to the bill — there is no `billId` on
  transactions, and adding one is a schema change explicitly out of scope in
  the spec. Once the undo toast is gone the created row is unfindable, and in
  the case this feature exists for the user has already deleted it themselves.
  Matching on amount, date and note would eventually delete the wrong row.
  Un-mark therefore clears the cycle and says so.
- **`manageRowHtml`'s signature is positional and long:**
  `(iconHtml, name, sub, amt, editAttr, deleteAttr, extraClass,
  actionsOverrideHtml, actionCount)`. Accounts passes `""` for `editAttr` and
  `deleteAttr` and supplies `actionsOverrideHtml` + `actionCount` instead
  (`settings-accounts.js:28`) — that is the call shape this row wants, since
  its actions are neither an edit nor a delete.
- **`actionCount` drives the reveal geometry**
  (`manage-row-swipe.js:17`, `12 + actionCount * 40 + (actionCount - 1) * 4`).
  Pass the real number; do not hardcode a width.
- **The full-swipe behaviour keys off a class,** `manage-swipe-delete`
  (`manage-row-swipe.js:33`, `:43-49`). Simply not using that class on these
  circles is what satisfies the no-full-swipe criterion — no new mechanism is
  needed to suppress it.
- **`state.manageSheetOpen` and Settings are not involved here.** Home has no
  manage sheet; this row's actions act directly.
- **Relevant tests:** `e2e/home.spec.js` already drives Home and uses
  `createBill`. `e2e/manage-row-swipe.spec.js` is the reference for asserting
  swipe reveal and tap-to-fire.
- **Do not change:** `markBillPaid()`'s behavior or its undo toast,
  `upcomingBills()` (`WI-030` owns that), `manage-row-swipe.js`'s drag physics,
  or any other screen's rows.
- **Escalate back to Claude if:**
  - `manageRowHtml` cannot express this row without changing its signature;
  - wiring `wireManageRowSwipe` on Home interferes with `wireTxRowActions()`
    (`home.js:306`) or with the hero carousel's own drag handling;
  - the desktop inline rendering of a single non-edit, non-delete action looks
    wrong enough to need a new primitive.

## Out of scope

- Remove-from-Home and the `dismissedCycle` field (`WI-032`).
- Any schema, mapper, or migration work.
- Push reminders and the Edge Function.
- Editing or deleting a bill from Home.
- Adding a `billId` to transactions.

## Dependencies

stays visible, and this ticket's "returns to its unpaid presentation" criterion
is written against the paid state `WI-030` introduces. Branch off whatever
`WI-030` lands on.
