## Goal

Marking a bill paid stops making it silently disappear from Home. The row stays
for the cycle it was paid for, visibly in a paid state, then leaves on its own
when the cycle turns.

## Why this is release 1 of 3

`WI-031` puts an Un-mark control on this row and `WI-032` adds Remove. Neither
has anywhere to live until a paid row is still on screen, so this lands first
and alone — see the spec's Releases section.

## Acceptance criteria

- [ ] `upcomingBills()` (`derived.js:316-320`) keeps a bill whose
      `lastPaidCycle` equals the cycle it was paid for, instead of dropping it
      when `nextBillDueDate()` rolls its date into next month and `daysUntil`
      exceeds 7.
- [ ] That bill leaves the list once the cycle turns over — the paid row is
      cycle-scoped, not sticky. A bill paid for September is gone from Home on
      1 October, same as today.
- [ ] An unpaid bill's presence, ordering, and `daysUntil` are **unchanged**,
      including the overdue case (negative `daysUntil` still passes the filter).
- [ ] Home's bill row shows the paid state in its `sub` slot and carries a
      modifier class on the row, mirroring how an archived account renders
      (`settings-accounts.js:28` uses `archivedLabel` plus
      `manage-row-archived`).
- [ ] The "Mark paid" button (`home.js:280`) is **not rendered** on a row
      already in the paid state — marking it again is meaningless.
- [ ] Sort order still puts the most urgent bill first. Decide and state in
      Review notes where a paid row sorts; `daysUntil` for a paid bill is next
      month's, so it naturally sorts last, and that is acceptable if
      deliberate.
- [ ] One new `STRINGS` key for the paid state word, both languages, following
      `archivedLabel` (`i18n.js:179`).
- [ ] `nextBillDueDate`, `daysUntilBillDue` and `billDueCycle` are **not
      touched** — see Do not change.
- [ ] No new CSS primitive beyond one modifier class, no new icon, no new
      control.

## UX / design references

- Follow `docs/UX.md`.
- Match existing: an archived account row (`settings-accounts.js:20-29`) — a
  state word in `sub`, a modifier class on the row.
- Reuse: the existing `.manage-row` / `.info` / `.sub` / `.amt` markup Home's
  bill row already uses (`home.js:270-283`), and
  `manage-row-overdue`'s styling approach for the new modifier class.
- New design primitives required by this ticket: none.
- Mobile (<1024px) behavior: as today, plus the paid row remaining visible.
- Desktop (>=1024px) behavior: identical to mobile here; this row is not
  viewport-dependent yet (`WI-031` is what introduces that split).

## Implementation guidance

- **Likely files:** `src/derived.js` (`upcomingBills`, `:316-320`),
  `src/screens/home.js` (the `dueSoon.map` block, `:270-283`), `src/i18n.js`,
  `styles.css`, `tests/derived.test.js`.
- **The filter is the whole ticket.** Today it is
  `daysUntil <= 7 && lastPaidCycle !== dueCycle`. Read the comment directly
  above it (`:309-315`) before editing: it explains that the second clause is a
  defensive backstop and that the *first* clause is what actually excludes paid
  bills, because `nextBillDueDate()` rolls a paid bill forward. Any fix that
  only relaxes the second clause will not work.
- **"The cycle it was paid for" is not `billDueCycle(bill)` once it is paid.**
  `billDueCycle()` returns the month of `nextBillDueDate()`, which for a paid
  bill is already *next* month (`tests/derived.test.js:78` asserts exactly
  this). The cycle the bill was paid for is `lastPaidCycle` itself. Getting this
  backwards produces a filter that never matches — derive the comparison from
  the current month, not from `billDueCycle()`.
- **`tests/derived.test.js` already has the fixtures for this.** It imports
  `upcomingBills` and drives `nextBillDueDate`/`billDueCycle` with mocked time
  (`:38`, `:48`, `:75-78`). Add cases there; no new harness is needed.
- **Known invariant:** an overdue bill has negative `daysUntil` and must still
  appear. The existing comment at `:309-310` calls this out specifically
  because it has been broken before.
- **Do not change:** `nextBillDueDate`, `daysUntilBillDue`, or `billDueCycle`.
  `supabase/functions/send-bill-reminders/index.ts:19-47` is a hand-kept
  faithful port of all three; editing them here silently desyncs push reminders
  from the UI. `upcomingBills()` has no counterpart there, which is exactly why
  it is the seam this ticket uses.
- **Do not change:** `markBillPaid()` (`home.js:32-70`) or its undo toast.
- **Escalate back to Claude if:**
  - keeping the paid row requires touching any of the three ported date
    functions;
  - the paid row cannot be expressed without a new layout primitive;
  - an existing `tests/derived.test.js` case has to change its expectation
    rather than gain a sibling.
