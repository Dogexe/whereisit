# WI-017 — Accent palette: Indigo (Purple) relabeled, Coral retuned

Status: Completed — **shipped in three rounds, see Review notes for all.**
Merged (commit `35f8228` and preceding round commits), pushed to `main`,
deployed.

Spec: `docs/specs/color-palette-refresh.md`

Codex profile: terra-medium

## Goal

The "Purple" accent option is relabeled so it no longer reads as
"violet"; "Coral" shifts away from its old red-leaning hue so it doesn't
read as close to the new expense-red (WI-016). No new accent option, no
change to how accent selection is stored or applied.

**Round 1** (flat Tailwind blue + amber) was rejected on sight by the
maintainer, who supplied two concrete reference images instead. **Round 2**
pixel-samples those references directly and lands on: Purple's *hex is
unchanged* from the app's original violet (`#6247ea` — it exactly matches
the reference's own accent, sampled via canvas), just relabeled "Indigo";
Coral becomes a Claude-brand-inspired terracotta, darkened to clear 4.5:1
white-text contrast. **Round 3**: the maintainer rejected round 2's
darkened Coral too ("coral is too dark bro and the gradient is odd") and
explicitly chose to keep the lighter, truer brand hue (`#D97757`) and
defer the resulting white-text contrast shortfall to a later text-shadow
fix rather than accept a muddier color — see Review notes for all three
rounds and `docs/UX.md`'s Known UI debt for the tracked gap.

### Round 2 (superseded by Round 3's coral value — kept for history)

The maintainer rejected Round 1 outright: *"wtf is that coral, i expect
somthing like claude color accent, the blue is so finance app stereotype,
i want kind of indigo. you can follow this one."* — with two reference
images (a finance-app screenshot and a 10-step color-ramp swatch panel
with two gradient bars).

- **Measured, not re-guessed:** rather than eyeballing the references,
  copied both images to a servable path (the originals lived under a
  Thai-named OneDrive folder a local Python server couldn't bind to —
  worked around by copying into the scratchpad dir) and loaded them in a
  real Chrome tab, then used `canvas.drawImage()` +
  `ctx.getImageData()` to read exact pixel RGB values at the FAB button,
  active tab icon, hero card gradient, and the swatch's 10 steps and two
  gradient bars — the same "canvas getImageData against real Chrome, not
  hand-converted" method `theme.js`'s own header comment already
  documents for the original coral pass.
- **Indigo finding:** the reference screenshot's FAB button and active tab
  icon sampled as *exactly* `#6247ea` at every point checked — this app's
  own pre-Round-1 purple base. So "indigo" wasn't a new hue to invent; it
  was reverting Round 1's flat-blue detour and keeping the app's original
  violet-blue, just correctly *labeled* "Indigo" instead of "Purple" (or
  Round 1's "Blue," which was the actual mismatch — the hue was never the
  problem, the name was). The reference's own hero-card gradient sampled
  to roughly `#604beb -> #4779ee/#66a0f9`, and the swatch's gradient bar to
  roughly `#5d4deb -> #409be8` — both close enough to this app's existing
  `#7b68ee -> #4f7df3` hero pair (already unchanged through Round 1) to
  confirm it was never the problem either.
- **Coral finding:** the maintainer asked for "something like claude color
  accent" — Anthropic's own warm terracotta/clay brand hue (approximated
  here as `#CC785C`/`#DA7756`, the values commonly seen in Claude's own
  UI). That literal value measures only 3.1-3.3:1 against white text,
  below this app's 4.5:1 floor — the exact same problem the *original*
  2024 coral pass hit (documented in `theme.js`'s pre-existing comment:
  its design spec's `oklch(62% 0.18 40)` measured 3.94:1, fixed by
  darkening to 58% L). Solved the same way here: held hue (15deg) and
  saturation (52%) fixed, walked lightness down from the reference's ~58%
  to 46% — `#B25738`, 4.87:1 white text. `c600`/`c700` follow the same
  hue/sat ladder at L36%/L24%.
- Full Round 2 measured contrast:
  | | base vs white | c600 vs card (light) | c600 vs card (dark) | c600 vs own tint | c700 vs own tint |
  |---|---|---|---|---|---|
  | Indigo | 5.82:1 | 7.51:1 | 2.19:1 (pre-existing, see Round 1 notes) | 6.31:1 | 8.38:1 |
  | Coral | 4.87:1 | 7.05:1 | 2.33:1 (pre-existing, see Round 1 notes) | 6.03:1 | 9.66:1 |
- `e2e/dark-mode.spec.js`'s hardcoded-hex assertion (fixed once already in
  Round 1) needed updating again — this time it round-trips back to the
  *original* values it had before Round 1 ever ran
  (`rgb(98, 71, 234)`/`#6247ea`), so no new computation was needed, just a
  revert of that one line.
- Live-verified in a real browser: rebuilt `dist/`, served locally,
  switched the accent preference between Coral and Indigo via the actual
  Settings UI, confirmed the Settings labels read "Coral"/"Indigo" (not
  "Blue"), and confirmed Indigo's hero card now visually matches the
  reference screenshot's violet-to-blue gradient while Coral reads as a
  warm terracotta clearly distinct from the expense-red amount shown on
  the same Home screen.
- `npm test` (173 passed), `npm run test:e2e` (31/31 passed — one hardcoded
  hex fixed, see above), `npm run build` all reran clean after Round 2.
- Diff scope for Round 2: same five files as Round 1 (`src/theme.js`,

### Round 3 (current — supersedes Round 2's coral value)

The maintainer rejected Round 2's coral too: *"coral is too dark bro and
the gradient is odd, fix the color first, white text problem can be fix
later by adding some shadows. left gradient for wi-018."* Three explicit
instructions, followed exactly:

1. **Fix the color, not the contrast workaround.** Round 2 darkened the
   Claude-brand hue (46% L) specifically so white button/chip text would
   clear 4.5:1 — trading true brand color for accessibility. The maintainer
   said do the opposite: keep the lighter, truer hue and accept the
   contrast shortfall for now. New `coral.base`: `#D97757` (hue 15deg, sat
   63%, L60% — the un-darkened brand hue Round 2 started from before
   darkening it). Measures **3.12:1 against white text — below this app's
   normal 4.5:1 floor, and left that way deliberately**, not silently.
2. **"White text problem can be fixed later by adding some shadows"** —
   an explicit, maintainer-authorized deferral, not an oversight. Added a
   `docs/UX.md` Known UI debt bullet naming exactly this gap (which
   token, which contrast measured, what the planned fix is) so it's
   trackable and doesn't silently rot into "nobody remembers why this is
   broken." Not yet turned into its own ticket — the maintainer said
   "later," not "now."
3. **"Left gradient for wi-018"** — did not touch the hero gradient
   *mechanism* (still `heroStart: base, heroEnd: c700`, the same
   convention used since the original coral pass). The "odd" gradient
   Round 2 produced (`#B25738 -> #5D2D1D`, a muddy dark-brown-to-darker-
   brown transition) naturally resolves into a brighter terracotta-to-rust
   gradient (`#D97757 -> #74311A`) purely as a side effect of fixing the
   base color — no bespoke gradient redesign was done or attempted here;
   any further gradient-specific work belongs to WI-018 per the
   maintainer's own instruction.
- **`c600`/`c700` were not relaxed the same way as `base`,** because
  they're a different failure mode: `base` pairs with *white* text
  (buttons, active chip/tab, hero balance text) — the thing being
  deferred. `c600`/`c700` render as *colored* text on `--color-card`/
  `--color-accent-tint` (`.btn-ghost`, `.badge-brand`,
  `.shortcut-btn.active`, `.picker-year-heading:hover`,
  `.kind-toggle button.active`) — illegible text there isn't part of what
  the maintainer asked to defer, so those still needed to clear their own
  floor on their own merits. Computed at the same hue/saturation as the
  new base, walked down in lightness: `c600` `#B74D2A` (L44%, 4.53:1
  against `--color-accent-tint`, 5.11:1 against `--color-card` light
  mode), `c700` `#74311A` (L28%, 8.47:1 against the tint).
- Live-verified in a real browser: rebuilt `dist/`, served locally,
  switched to Coral, confirmed the hero card/active nav/active pill now
  read as a vivid terracotta (not muddy brown) and that white balance
  text, while lower-contrast than everywhere else in the app, is still
  legible against the new lighter fill.
