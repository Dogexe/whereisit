# WI-015 — Grouped-card styling for Settings' Manage sub-page rows

Status: Completed

Implemented by Claude, not Codex — the maintainer explicitly asked Claude
to implement this ticket directly because Codex's quota was exhausted.
Merged in commit `f4277a1` (pushed to `main` alongside `WI-011`), deployed,
and confirmed both via the live bundle and by the maintainer directly on
a real mobile browser.

Spec: `docs/specs/settings-manage-rows-card-styling.md`

Codex profile: terra-medium

Profile reason: bounded presentational CSS/markup work reusing existing
primitives (`.list-card`, `.settings-section-label`). It touches no
state, no navigation, and no swipe/drag logic — only the surrounding
chrome around rows `WI-005` and `WI-011` already own.

## Goal

Wrap each Manage sub-page's row list (Budgets, Bills, Goals,
Categories, Accounts) in the same `.list-card` treatment the Settings
root list and the Security sub-page already use, so every Settings
screen reads as one consistent design system.

**Chrome only.** No change to row content, sizing, icon avatars, swipe
gesture/reveal math, or the FAB's position/behavior.

## Acceptance criteria

- [ ] No section label is rendered above a Manage sub-page's row list —
      the sub-page header's own title is the only heading, matching
      Security's actual mobile behavior (its `.settings-section-label`
      is desktop-only, hidden on mobile by an existing CSS rule).
- [ ] Each Manage sub-page's row list renders inside a card that picks
      up `.list-card`'s shared `background` / `border-radius` /
      `box-shadow` (styles.css line ~197) and its `4px 14px` padding —
      the same visual container the root list's groups and the Security
      sub-page already use.
- [ ] The shared `.list-card` rule itself is **not** modified — every
      other card in the app (Home, Insights, goal cards, etc.) must be
      pixel-unchanged.
- [ ] `.manage-row`'s own padding/font-sizing is unchanged (already
      matches `.toggle-row`'s `12px 4px` / 15px name).
- [ ] A swipe-revealed action on the **first or last** row of a sub-page
      (full reveal and full-swipe-to-delete) stays visually clipped to
      the new card's rounded corners — no square edge poking past the
      curve. Scope this clipping to the new wrapper only; do not add
      `overflow: hidden` to the shared `.list-card` rule.
- [ ] `WI-005`'s swipe mechanics are unaffected: reveal width formula,
      40px circular action buttons, pop-in/grow animation, linear drag,
      full-swipe-to-delete at 65%, snap-back on release between reveal
      and commit — all identical to today, verified live on at least
      one 2-button section and Accounts (3-button).
- [ ] `WI-011`'s FAB still renders in the same fixed bottom-right
      position and opens the correct Manage sheet on each of the five
      sub-pages — confirm live that wrapping the rows in a new card
      element didn't introduce a `transform`/`filter` ancestor that
      would change the FAB's fixed-position containing block.
- [ ] Categories' grouped/nested rows and Goals' card-shaped rows
      (`goal-card-top-content`) render and swipe correctly inside the
      new card.
- [ ] An empty section (e.g. zero budgets) renders its empty-state text
      inside the card, not floating outside it.
- [ ] The Security sub-page and the Settings root list are pixel-
      unchanged — they already have this treatment.
- [ ] Desktop (1024px+) is pixel-unchanged.
- [ ] Light and dark mode both render correctly: card background,
      section-label contrast, and inter-row divider lines.
- [ ] `renderManageSheet`, `wireInlineCrud`, and the six `xFormHtml()`
      modules are not modified. (`manage-row-swipe.js` *and* `tx-row.js`
      were both modified — see Review notes "Two defects found" and
      "Seventh": a pre-existing hover-fallback defect found during this
      ticket's own verification was fixed in both files, since
      `docs/UX.md` requires the two swipe surfaces to stay behaviorally
      identical and fixing only one would have violated that. Done per
      explicit maintainer request, overriding this criterion's original
      scope.)
- [ ] `.settings-manage-header` / `.settings-security-subpage-header`
      markup and styling are not modified.

## Review notes

### Fourth defect: Goals was left out, and it showed

The first three passes above only ever populated Budgets/Bills/Categories/
Accounts to verify, because a first attempt at wrapping Goals seemed
architecturally awkward — each Goal already renders as its own
individually-carded `.goal-card`, so wrapping the set in a second outer
`.list-card` looked like nesting a card inside a card. That reasoning
produced a version of this ticket (see the superseded "Scope refinement"
note this replaces) that **excluded Goals from the unified card
entirely**. The maintainer added real goals through the UI, looked at
the Goals sub-page, and confirmed it visibly "behaved different" from
the other four: loose floating cards with visible gaps, instead of one
unified divided list.

**Fix**: Goals is now wrapped in the same `.manage-rows-card` as the
other four sections. Since `.goal-card` is used nowhere else in the app
(confirmed by grep — `goalCardHtml()` in `src/screens/settings-goals.js`
is its only producer), its independent card styling is safely flattened
*only inside* `.manage-rows-card`: transparent background, no shadow,
the same `12px 4px` divider-row padding and `border-bottom` every other
manage row uses, and `.insight-cards`' normal 14px inter-card gap zeroed
in this one context so goals sit flush like every other row.
`goalCardHtml()` itself was not touched — this is a pure CSS override
plus the same wrapper `<div>` the other four sections now get.
`docs/specs/settings-manage-rows-card-styling.md`'s Decision 0 (new)
records this; Decision 2 was corrected to note the one exception.

**Verified live** on a served `dist/` build with two real goals added
through the Add-goal sheet: Goals now renders as one rounded card with a
thin divider between goals, matching Budgets/Bills/Categories/Accounts.
Re-checked swipe (reveal and full-swipe-delete grow and clip correctly,
identical to the other sections) and dark mode (card background and
divider render correctly) on the flattened row — no regression to
Goals' progress bar, badge, or Contribute button, none of which were
touched. Re-ran `npm test` (173/173), `npm run test:e2e` (28/28),
`npm run build` — all clean.

Verified live: populated Goals (two goals added through the sheet)

shows the single card with the empty-state message. Re-ran `npm test`
(173/173), `npm run test:e2e` (28/28), `npm run build` — all clean.

### Sixth: icon-avatar size inconsistency across Manage rows (maintainer-reported, confirmed and fixed)

The maintainer separately reported "the icon seem too small from
normal" and asked to check the other sub-pages too. Measured live with
`getBoundingClientRect()`: Budgets/Categories/Accounts (and, by the same
shared code path, Bills) rendered their leading category icon at a
**30×30px** `.icon-avatar` (the `"sm"` size class, with an explicit
`width="15" height="15"` glyph override) — a pre-existing choice from
`docs/specs/settings-manage-row-icons.md`, unrelated to and pre-dating
this ticket. Every other icon avatar in the app (Transactions rows,
Home, and — not incidentally — Goals, whose bigger icon is what made
the mismatch obvious once the two sub-pages started looking similar)
renders at the default **40×40px** with an 18px glyph. This is a real,
measurable inconsistency, confirmed live rather than assumed.

**Fix**: removed the `"sm"` size class and the explicit `width="15"
height="15"` glyph override from the three call sites that had them —
`categoryIconAvatar()` in `src/screens/manage-row.js` (shared by
`budgetRowHtml` and `billRowHtml`), `accountRowHtml()` in
`src/screens/settings-accounts.js`, and `categoryRowHtml()` in
`src/screens/settings-categories.js` — so all three now call
`iconAvatar(...)` with no size arguments, falling through to the same
40px/18px default every other icon avatar in the app already uses. No
new CSS, no new tokens — this only removes an override, it doesn't add
one. This does revisit `docs/specs/settings-manage-row-icons.md`'s
sizing (though not its icon-choice/color decision), and touches files
outside this ticket's original scope; done per explicit maintainer
request during this review pass, same as the earlier `manage-row-swipe.js`
fix above.

Verified live on Budgets, Bills, Categories (including its indented
child-category rows — `.manage-row-child` only adds left padding, so a
bigger icon doesn't crowd anything), and Accounts: icons now render
visibly larger and consistent with Goals/Transactions, no text
overlap, wrapping, or layout breakage. Re-ran `npm test` (173/173),
`npm run test:e2e` (28/28), `npm run build` — all clean.

### Two defects found and fixed after maintainer review of the first pass

The maintainer reviewed the first implementation live and flagged two
problems with a screenshot: a repeated "BUDGETS" label directly under
the "Budgets" header, and a stray empty area at the bottom of the card.

**1. Redundant section label — removed.** The first pass added a
`.settings-section-label` above each of the five sub-pages' row lists,
reasoning (spec Decision 3, now corrected) that Security already ships
an identical repeated label. That reasoning was wrong: Security's label
is hidden on mobile by an existing CSS rule
(`.settings-layout[data-mobile-subpage="security"] [data-settings-panel="security"]
> .settings-section-label { display: none; }`) and only ever shows on
desktop, where it's the pane's sole heading. Fix: removed the label
markup entirely from the five sections on mobile (`src/screens/settings.js`)
— no equivalent CSS suppression needed since the markup is now
conditionally omitted at the source. See the spec's corrected Decision 3.

**2. Stray blank/broken row — root-caused and fixed.** What looked like
empty space was actually a Manage row stuck permanently "swiped open"
(this session's earlier report called it a "pre-existing defect,
unfixed" — it has now been root-caused). Traced to
`manage-row-swipe.js`'s `pointerenter`/`pointerleave` "desktop mouse
fallback," added by `WI-005` to mirror `tx-row.js`'s hover-reveal "in
case a mouse is used in a narrow/resized desktop browser window." That
scenario is exactly how both the maintainer and this session's own
Playwright verification reproduced it: a click that re-renders the DOM
(e.g. drilling into a sub-page) can leave the real cursor sitting over a
newly-rendered row it never deliberately hovered, and the browser
resynthesizes a `pointerenter` for whatever now sits under a stationary
cursor after the layout change — which calls `openRowTo()` and
permanently reveals that row's actions with no real user gesture.
Confirmed via `git stash` that this already existed identically before
WI-015; this ticket's card styling only made the resulting blank space
more visually obvious inside a clean rounded card. Unlike `tx-row.js`
(rows render at every viewport width, a real first-class-mouse surface),
this module is wired only below 1024px, where the only realistic input
is touch, so the fallback had no real audience and only a real failure
mode. Fixed by deleting the `pointerenter`/`pointerleave` block from
`wireManageRowSwipe()` — swipe-to-reveal now only ever responds to an
actual drag gesture. This modifies `manage-row-swipe.js`, which this
ticket originally listed as untouched; the maintainer explicitly asked
for this fix during review, overriding that scope line. Documented in
`docs/specs/settings-manage-swipe-and-sheet.md`'s new "Correction"
section.

**Re-verification after both fixes**: `npm test` (173/173), `npm run
test:e2e` (28/28, including `manage-row-swipe.spec.js` and
`transactions-crud.spec.js`'s swipe specs — `tx-row.js` was left with
its own copy of the same hover fallback at this point, which "Seventh"
below later corrected for `docs/UX.md` parity), `npm run build` — all
clean.
Live-rechecked on a fresh Chromium instance at 390×844: no section label
renders under any of the five sub-page headers, and repeated fresh loads
of Budgets/Bills/Categories/Accounts no longer show any row stuck open.

### Third defect: the maintainer reported the blank space was still there after the above

The stuck-open-row fix above was real but was not the actual cause of
what the maintainer's screenshot showed — that screenshot's blank area
had no visible edit/delete buttons at all, just empty white space,
which doesn't match a stuck-open row's signature (this session's own
earlier test data happened to reproduce both bugs at once, which is
what conflated them).

**Actual root cause**: the first implementation put the `list-card`
class directly on `.settings-manage-body` — the same element
`WI-011` targets with `body.settings-subpage-open .settings-manage-body
{ padding-bottom: calc(...) }` to keep the FAB clear of the last row.
With `.settings-manage-body` doubling as the visual card, that padding
rendered *inside* the rounded card, as a large empty area right before
its bottom corner — exactly the blank space in both of the maintainer's
screenshots.

**Fix**: `.settings-manage-body` reverts to a plain, unstyled scroll
container (its original pre-WI-015 shape). A new inner element,
`<div class="list-card manage-rows-card">`, wraps only the row list for
Budgets/Bills/Categories/Accounts; the FAB-clearance padding stays on
the outer `.settings-manage-body`, so it now renders in the page
background *below* the rounded card, not inside it. `styles.css`'s
corner-clipping rule (Decision 4) moved from the removed
`.settings-manage-body.list-card` compound selector to the new
`.manage-rows-card` class. `src/screens/settings.js` gained four small
local consts (`budgetsRowsHtml`, `billsRowsHtml`, `categoriesRowsHtml`,
`accountsRowsHtml`) so each section's row markup is computed once and
reused for both the desktop (bare) and mobile (card-wrapped) branches.

Verified with `getBoundingClientRect()` against a served `dist/` build:
`.manage-rows-card`'s `padding-bottom` is the plain `.list-card` value
(4px) and its bottom edge sits flush after the last row; the outer
`.settings-manage-body`'s `padding-bottom` is the full FAB-clearance
value (68px in this build) and extends well past the card's bottom
edge. Screenshot confirms the card now hugs its rows tightly with the
FAB-clearance gap visible in the page background beneath it, not as
dead space inside the card. Re-ran `npm test` (173/173), `npm run
test:e2e` (28/28), `npm run build` — all clean.

### Seventh: docs/UX.md wasn't actually read until asked — surfaced a real compliance gap in the "Sixth" swipe-hover fix

The maintainer asked directly whether `docs/UX.md` had been read for
this work. It hadn't — only referenced as ticket-template boilerplate.
Reading it properly surfaced a real problem with the "Two defects found"
section's swipe-hover fix above: `docs/UX.md`'s Motion section states
Transactions rows and Settings Manage rows are "contractually
identical... any visible difference between the two is a bug." That fix
removed the dead/buggy `pointerenter`/`pointerleave` hover fallback from
`manage-row-swipe.js` only, leaving `tx-row.js`'s byte-identical copy in
place — exactly the prohibited asymmetry.

Investigated whether `tx-row.js`'s copy was actually load-bearing before
touching the app's primary Transactions screen: `styles.css`'s
`.tx-list-card` desktop override (1024px+) already makes `.tx-row-actions`
`position: static`, an always-visible column, independent of hover or
drag — this is `docs/specs/settings-manage-swipe-and-sheet.md`'s own
"dense table" decision, already shipped. So `tx-row.js`'s hover fallback
was never reachable on the real desktop Transactions table either; its
only reachable audience was the identical narrow/resized-mouse edge case
as the Settings copy, with the identical phantom-`pointerenter`-after-
rerender failure mode. Confirmed with the maintainer before touching a
higher-traffic file outside this ticket's scope, then removed it from
`tx-row.js` too.

**Verification**: `npm test` (173/173), `npm run test:e2e` (28/28,
including `transactions-crud.spec.js`'s `row.hover()` → edit and
`row.hover()` → delete tests, and `transfers.spec.js`'s `.hover()`
call — all still pass because they run at the suite's default desktop
viewport, where `.tx-list-card`'s static column already makes Edit/
Delete clickable with no hover needed; their `.hover()` was already
inert before this change), `npm run build` — all clean. Live-checked
with a real browser: the desktop Transactions dense-table still shows
Edit/Delete as an always-visible column (unaffected); hovering a Home
recent-activity row (same `.tx-row-wrap` markup, not wrapped in
`.tx-list-card`, the one path with no automated coverage either way) no

correction" section.
