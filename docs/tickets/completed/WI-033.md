# WI-033 — Give themed color tokens one owner: styles.css

Status: Completed

Spec: none — pure refactor, no product change. The one standing decision it
reverses (`docs/UX.md`'s Design-token ownership) is recorded under
Dependencies; maintainer approval for it was granted 2026-09-12.

Codex profile: terra-medium

Profile reason: the work is mechanical transcription of values that already
exist, with no state, persistence, or sync involved. The risk here is a
dropped token, which verification catches — not reasoning depth. (The Risk
tier below is High for a different reason and is deliberately not coupled to
this field.)

Risk tier: High

## Goal

Every themed color token is declared once, in `styles.css`. `applyTheme()`
stops writing colors and shrinks to setting two attributes on `<html>` plus
the `theme-color` meta tag. The "keep these two files in sync by hand"
requirement disappears.

## Why now

The two-owner model has already drifted, and it is visible on every cold load:

| Token | `styles.css:69` (first paint) | `theme.js:100` (runtime, coral) |
|---|---|---|
| `--hero-gradient-end` | `#74311A` (dark brown) | `#D6A44C` (gold) |

Home's hero card paints coral→brown, then repaints coral→gold when `main.js:52`
runs.

This is not a new discovery — `docs/UX.md:298-306` already carries it as
accepted known debt, with the prescribed fix ("update `styles.css`'s `:root`
`--hero-gradient-end` to `#D6A44C` to match") and the note that it violates the
Design-token ownership rule. That is the point: the sync rule was written down,
the drift against it was found, it was recorded, and it was *still* left in
place because keeping two files in step by hand is work nobody schedules.
Deleting the second owner resolves that debt item permanently instead of
re-fixing one token and leaving the mechanism intact.

## Implementation guidance

- **Likely files:** `src/theme.js`, `styles.css`, `docs/UX.md`. Nothing else
  should need to change.
- **`applyTheme()`'s two call sites stay as they are:** `main.js:52` (boot) and
  `settings.js:445-446` (the accent and appearance radios). Both still need to
  run — they now flip attributes instead of writing 22 properties.
- **Why attributes on `<html>` and not a class:** two independent axes (theme,
  accent) read more clearly as two attributes, and `:root[data-theme="dark"]`
  outranks bare `:root` on specificity without `!important`.
- **The old code wrote inline styles on `documentElement`,** which outrank any
  stylesheet rule. Deleting the `setProperty` calls is sufficient — inline
  styles are not persisted, so there is no stale state to migrate and no
  cleanup pass needed on upgrade.
- **Existing regression guard:** `e2e/dark-mode.spec.js:4-29` already asserts
  `getComputedStyle(document.body).backgroundColor` is exactly
  `rgb(238, 240, 244)` light / `rgb(17, 18, 22)` dark after toggling the
  Settings switch. It is written against computed style, not against
  `theme.js`, so it should pass unmodified — if it needs editing to pass,
  something is wrong with the refactor, not with the test.
- **Known invariant:** `rowTone()`/`GOAL_TONES` (`categories.js`) and
  `CHART_COLORS` (`derived.js`) pass `var(--token)` **strings** into inline
  `style=` attributes. They must keep doing that — do not resolve them to hex.
- **Do not change:** any color's rendered value; the derived `*-tint` /
  `-tint-fg` tokens; `index.html:16`'s meta tag markup; the accent radio /
  appearance radio wiring in `settings.js`.
- **Escalate back to Claude if:**
  - a `*-tint` does not re-resolve against an overridden base (that would
    invalidate the whole approach — stop, don't work around it by
    duplicating tints into the dark block);
  - any token turns out to be read from JS as a hex rather than a
    `var()` string;
  - the first paint flashes in a *new* place after the change.

## Out of scope

## Review notes

Implemented directly by Claude at explicit maintainer instruction (bypassing
Codex, as with WI-016/017/018/019), so there is no independent-review round to
record here. What follows is what the implementation found that the ticket did
not already say.

**The ticket's "Why now" was wrong on one point, corrected before
implementation.** It framed the `--hero-gradient-end` drift as undetected
("nothing detects this"). It had in fact been detected, written up in
`docs/UX.md`'s Known UI debt with the exact one-token fix prescribed, and
accepted. That makes the case for the refactor stronger, not weaker — the sync
rule existed, the violation was recorded against it, and it still sat there —
but the ticket said something untrue about the repo and was fixed before any
code changed. Two acceptance criteria were added at the same time: delete the
now-resolved debt bullet, and preserve the palette provenance comment rather
than deleting it with the code.

**`theme.js`'s 96-line comment block was load-bearing, not decoration.** It
held the measured contrast ratios for both accents, including which values are
*deliberately* below the 4.5:1 floor and must not be "fixed" by darkening.
Deleting it along with the `ACCENT` map would have destroyed the only
in-code record of an accessibility decision. The operative facts moved into
`styles.css` beside the tokens; the narrative stays in the two specs.

**The `theme-color` meta tag nearly reintroduced the bug.** The first pass
wrote `state.dark ? "#111216" : "#eef0f4"` in `applyTheme()` — a second copy
of two background hexes, in the same file the refactor was emptying. It now
reads `--color-bg` back out of the stylesheet via `getComputedStyle`, which
sees the freshly-set attributes because that call forces the style recalc.

**The existing e2e guard was weaker than it looked.** The ticket named
`dark-mode.spec.js` the regression guard and required it to pass unmodified —
it did. But its assertions are on *rendered colors*, which are identical under
both the old and new arrangements, so it could not have caught a regression to
two owners. An assertion on `data-theme` plus a null inline style was added,
and confirmed to fail by temporarily reintroducing a `setProperty` call. A
guard never observed failing is not a guard.

**Verification note.** The before/after token capture initially used a baseline
taken with a slightly different harness (the service worker reloaded the page
mid-evaluate after a rebuild, so the after-run had to block service workers).
The baseline was re-taken with the identical script before comparing, rather
than comparing across two harnesses.

**Two comments elsewhere in `styles.css` were made stale by this change and
were fixed rather than logged** — `.sidebar-logo`'s, which said `theme.js` sets
`--logo-ring-color`, and the tab-bar Add button's, which pointed at
`theme.js`'s `ACCENT` comment for the gradient rationale. Neither was in the
ticket's stated scope, but this pass is what made them wrong, and shipping
newly-stale comments while deleting a second owner in the name of preventing
exactly that would have been incoherent.

Optional suggestions, not defects, deliberately not acted on here:

- The remaining audit findings (six `pull*` functions in `sync.js`, five
  `delete*` functions in `settings-*.js`, six sheets' duplicated plumbing) are
  untouched and still stand.
