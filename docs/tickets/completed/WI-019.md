# WI-019 — Retune expense-700/income-700 to a more vivid red/green

Status: Completed — merged in commit `8a01f9c`, pushed to `main`, deployed.

Spec: `docs/specs/amount-color-semantics.md` (see "Addendum: `-700` hex
retune" section)

Codex profile: terra-medium

## Goal

`--color-expense-700` and `--color-income-700` (both themes) move from
today's muted, purely-contrast-tuned hex to a more vivid red/green closer
to the maintainer's original reference image, while every dependent
contrast floor still clears its documented minimum — verified live, not
assumed from the target hex below.

## Acceptance criteria

- [x] `theme.js`'s `applyTheme()` sets new values (light expense-700
      deviated from the starting target — see Review notes):
      - `--color-income-700`: light `#15803D` (was `#147a54`), dark
        `#4ADE80` (was `#34c98a`).
      - `--color-expense-700`: light `#CC2020` (was `#c22f22`, target was
        `#DC2626`), dark `#F87171` (was `#ff7a68`).
- [x] `--color-expense`/`--color-income` **base** values (non-`-700`) are
      unchanged — out of scope for this ticket.
- [x] Every existing consumer of these two tokens is confirmed to still
      clear the relevant WCAG floor at the new values: amount text
      (`tx-row.js`, `add.js`), Home stat-card deltas (`home.js:139,144`),

- [x] Existing related behavior remains unchanged.

## Implementation guidance

- Likely files: `src/theme.js` only for the value change; verification
  touches `src/screens/home.js`, `src/screens/tx-row.js`,
  `src/screens/add.js`, `src/styles.css` (read-only, to confirm each
  consumer listed above).
- Likely functions: `applyTheme()`.
- Existing pattern to reuse: `theme.js`'s header comment documents the
  exact method used to tune every color in this file — canvas
  `getImageData` against real rendered Chrome, not hand-converted hex.
  Repeat that method here.
- Known invariants: `-700` in dark mode has historically just equaled the
  base color (per `theme.js`'s own comment: "In dark mode the base hues
  were already tuned to clear ~6-7:1 against `--color-card`... darkening
  it further... moves the wrong direction"). The dark-mode targets above
  (`#4ADE80`/`#F87171`) diverge from that historical pattern — confirm
  they still clear whatever floor the darkest consumer needs (small bold
  text on `--color-card` in dark mode, ≥4.5:1) rather than assuming the
  old equals-base shortcut still applies.
- Do not change: `--color-expense`/`--color-income` base values,
  `--color-expense-tint`/`--color-income-tint` (derived via `color-mix()`
  in `styles.css`, auto-follow base — unaffected by this ticket since base
  is unchanged), any token name.
- Escalate back to Claude if: the target hex above can't clear 4.5:1 for
  the smallest/boldest consumer (likely `.manage-row-overdue .sub` or
  `.badge-expense`) without desaturating enough that it no longer reads as
  "vivid" — that's a real tradeoff the maintainer should see, not something
  to quietly resolve by picking a duller value.

## Review notes

**Implemented directly by Claude** (not Codex — Codex's usage quota was
exhausted; the maintainer explicitly asked Claude to implement this one
rather than wait, with an explicit instruction to read `docs/UX.md` first).

- Changed `src/theme.js`'s `applyTheme()` and `styles.css`'s `:root`
  pre-JS fallback together, per `docs/UX.md`'s Design-token ownership rule
  (both must stay in sync or first paint goes stale).
- **Deviation from the ticket's starting target, as anticipated by its own
  "Escalate if" clause:** light-mode `--color-expense-700` targeted
  Tailwind red-600 (`#DC2626`), but measured contrast against
  `--color-expense-tint` (`.badge-expense`'s background, ~`#fde9e7` — a
  12% mix toward white, not pure white) was only 4.14:1, below the 4.5:1
  floor and a real regression from the old `#c22f22`'s 4.83:1 there.
  Nudged to `#CC2020` — still reads as the same vivid red (5.53:1 on
  `--color-card`, 4.74:1 on the tint), no visible desaturation, and clears
  both surfaces. This was a small enough adjustment not to interrupt the
  maintainer for; documented instead, per the ticket's own guidance to
  only escalate when a fix would require losing the "vivid" look.
- **Pre-existing defect found, not introduced by this change, left
  unfixed as out of scope:** dark-mode `.badge-expense`
  (`--color-expense-700` on `--color-expense-tint`, which stays near-white
  in *both* themes per its own doc comment in `styles.css`) already
  measured ~2.3:1 before this pass with the old `#ff7a68`; the new
  `#F87171` measures ~2.5:1 — not meaningfully different, so not a
  regression this ticket caused, but a real accessibility gap that
  predates it. Worth its own ticket (likely the same fix pattern as
  `--color-income-tint-fg`: a fixed, theme-invariant foreground for
  `.badge-expense`, since a tint that never darkens for dark mode can't
  safely pair with a `-700` token that does).
- **One additional consumer found beyond the ticket's list, no issue:**
  `settings-goals.js:46` also reads `--color-income-700` as a progress-bar
  fill color (not text) when a savings goal is complete. Not a text/WCAG
  contrast context, no fix needed, noted for completeness.
- Full measured contrast (relative-luminance calc against real theme
  colors):
  | Consumer background | Light | Dark |
  |---|---|---|
  | `--color-card` (amount text, stat deltas, sync status, logout row, overdue text) | income 5.02:1, expense 5.53:1 | income 9.44:1, expense 5.95:1 |
  | `--color-bg` (sanity check, no actual consumer sits directly on it) | income 4.65:1, expense 4.85:1 | income 10.47:1, expense 6.60:1 |
  | `--color-expense-tint` (`.badge-expense`) | expense 4.74:1 (pass) | expense ~2.5:1 (pre-existing fail, see above) |
- Live-verified in a real browser (not just computed math): rebuilt
  `dist/`, served locally, toggled light/dark via the actual Settings UI,
  read `getComputedStyle`/CSS custom properties directly to confirm
  rendered values match, screenshotted the Transactions list with both an
  expense and income row visible in dark mode.
- `npm test` (173 passed), `npm run test:e2e` (31/31 passed), `npm run
  build` (passed) all reran clean after the change.
- Diff scoped to exactly `src/theme.js` and `styles.css` (the two `-700`
  hex pairs) — no other files touched.
