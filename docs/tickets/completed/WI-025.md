# WI-025 — Make "Mark paid" reversible with an undo toast

Status: Completed

Spec: `docs/specs/reversible-mark-paid-and-announced-toasts.md`

Codex profile: sol-high

Profile reason: the undo path writes two persisted arrays and emits two sync
rows (a transaction tombstone and a bill row); a wrong `lastPaidCycle`
restore desyncs silently across devices rather than failing loudly.

## Goal

One click of "จ่ายเลย" / "Mark paid" can be taken back from the toast, undoing
**both** the expense it created and the bill's paid-for-this-cycle flag.

## Acceptance criteria

- [x] `markBillPaid()` (`src/screens/home.js:32`) shows its toast with an undo
      callback, so `#toastUndoBtn` is present after every mark-paid.
- [x] The undo callback removes the created transaction from `transactions`,
      saves, and re-renders.
- [x] The undo callback restores `bill.lastPaidCycle` to the value it held
      **before** the click — `null` on a first payment, the previous cycle key
      if the bill had been paid in an earlier month — not unconditionally to
      `null`.
- [x] The undo callback pushes both changes: a tombstone for the transaction
      (`pushDeleteTx`) and a fresh `billToRow(bill, false)`, then `syncNow()`.
      `bill.updatedAt` is refreshed so last-write-wins resolves the undo, not
      the mark-paid, on a second device.
- [x] After undo, Home shows the bill back in Upcoming bills with the same
      due/overdue label it had before the click, and the transaction is gone
      from Recent activity and from the Transactions list.
- [x] The toast message is `checkBudgetAlert(savedTx) || L().toastBillPaid`,
      with the undo callback attached **unconditionally** — a budget-over
      message still wins the text, and still offers Undo.
- [x] One new `STRINGS` key is added: `toastBillPaid`, `["บันทึกการจ่ายแล้ว",
      "Bill marked paid"]`.
- [x] No confirm dialog is added (`docs/UX.md`: "Undo over confirm").
- [x] `bill.lastPaidCycle` is still set to `billDueCycle(bill)` on the
      mark-paid path itself — the forward behavior is unchanged.
- [x] Existing related behavior remains unchanged.

**Confirmed defects: one, found on review and fixed.**

*Sync ordering — the forward and undo pushes were unordered.* As first
implemented, the mark-paid `Promise.all([pushTx, pushRows("bills", ...)])` and
the undo callback's `Promise.all([pushDeleteTx, pushRows("bills", ...)])` were
two independent network chains with no sequencing between them. `pushRows`
(`src/sync.js:154`) is a plain Supabase `upsert`, so the server has no
last-write-wins resolution — arrival order decides the stored row, not
`updated_at`. If the forward insert landed *after* the undo's tombstone, the
server kept `deleted:false`; `clearPending`'s reference-equality check had
already dropped the tombstone as successfully pushed, and `mergeRowsById`
(`src/merge.js:16`) re-adds any remote non-deleted row missing locally, so the
next pull silently resurrected the undone transaction and the stale bill row.
This is the exact silent-desync failure mode the ticket's `sol-high` profile
reason named.

Fixed by hoisting the forward push into a `forwardPush` variable before
`showToast` and chaining the undo's pushes off it, so the tombstone and the
restored bill row can never overtake the forward insert on the server.
`pushRows` swallows its own errors and returns `false` rather than rejecting,
so a failed forward push cannot drop the undo chain. Codex verified the
finding against the code before applying the fix, per `docs/WORKFLOW.md`.

Verification run by Claude after the fix, not taken from the implementer's
report:

- `npm test` — 173 pass, 0 fail (unchanged, as predicted).
- `npm run build` — clean.
- `npm run test:e2e` — 35 pass, 0 fail, including the new undo test.

Known gaps and residual risk, accepted rather than fixed:

- **Only the first-payment branch is tested.** The new e2e test covers
  `prevPaidCycle === null`. The prior-month branch — where restoring
  `lastPaidCycle` to `null` unconditionally would be wrong, and which is the
  whole reason the value is captured — has no coverage. `e2e/helpers.js:6`
  records this suite's convention of driving the real UI rather than seeding
  localStorage, and no UI produces a prior-month `lastPaidCycle`, so covering
  it needs either a seeding escape hatch in the fixtures or a testable seam in
  `markBillPaid`. Both are wider than this ticket. The code path was reviewed
  by reading, not by execution.
- **A transient local blip if Undo is clicked mid-push.** The forward chain's
  own `.then(() => syncNow())` is registered before the undo's, so when Undo is
  clicked while the forward push is still in flight, that pull can briefly
  re-add the transaction locally before the tombstone goes out, and the undo's
  trailing `syncNow()` may then no-op on `syncInFlight`. Server state ends up
  correct either way and the local copy clears on the next sync cycle. Closing
  it properly means restructuring `syncNow`, which this ticket puts out of
  scope.
- The e2e suite runs signed out with Supabase calls as no-ops, so none of the
  sync behavior above — including the ordering fix — is exercised by an
  automated test. It was reviewed against `sync.js`, `pending.js`, and
  `merge.js` by reading.
