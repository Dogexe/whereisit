# WI-021 — Home hero card: swipeable account carousel replaces chip row

Status: Completed

Spec: `docs/specs/home-hero-account-carousel.md`

Codex profile: sol-high

Profile reason: new gesture/drag code plus removal of the app's only
existing account-switching UI on Home — matches AGENTS.md's "state-
management changes"/"large refactor" criteria for `sol-high`, even though
`state.homeSelectedAccountId` itself is UI-only, since the failure mode
(broken swipe math, lost account-switch capability) isn't well understood
until built.

Risk tier: High

## Goal

Remove the account-chip row above Home's hero balance card; make the hero
card itself a swipeable/click-arrow carousel across "All accounts" + each
account, with hidden-until-interaction page dots and a per-page kicker
label ("Total balance" vs. the account's name).

## Acceptance criteria

- [ ] `accountSwitcherHtml()` and its call site are removed; no chip row
      renders above the hero card.
- [ ] The hero card has one page per account (All accounts first, then
      `accounts` in existing order, including archived accounts) — no
      wraparound past either edge.
- [ ] Swiping/dragging (touch) or clicking an arrow (desktop, >=1024px)
      or clicking a dot (both) changes `state.homeSelectedAccountId` and
      re-renders, exactly matching today's chip-click behavior — income/
      expense cards, spent-today, sparkline, and recent activity all
      update together with the hero card.
- [ ] Page dots: one per page, invisible at rest, fade in on
      drag-start/tap, auto-fade out ~1.5s after release with no further
      interaction, active dot visually distinct from inactive ones.
- [ ] Desktop (>=1024px): left/right arrow buttons always visible on the
      hero card (not hover-only), disabled/dimmed (not hidden) at the
      first/last page. Hidden on mobile widths.
- [ ] Kicker label is "Total balance" (new i18n key) on the all-accounts
      page, and the account's own `name` on each account page.
- [ ] `prefers-reduced-motion` disables the dot fade animation (instant
      toggle instead).
- [ ] Zero-account and one-account cases don't error (dots/arrows degrade
      gracefully per the spec's Out of scope note).
- [ ] `state.homeSelectedAccountId` stays UI-only/not persisted — reload
      resets the carousel to "All accounts."
- [ ] Existing related behavior remains unchanged: `computeBalance()` and
      every other derived-data function, the hide-amounts eye button, the
      sparkline/delta pill rendering logic for whichever page is active.

## UX / design references

- Follow `docs/UX.md`.
- Match existing: `.hero-card` (`src/screens/home.js`, `styles.css`
  ~line 395) for card visual treatment; `.btn-icon` for the desktop
  arrows; the drag/50%-snap-threshold math from
  `docs/specs/swipe-to-reveal-transaction-actions.md` Revisions 1-2 as
  the closest existing "draggable with a commit threshold" reference in
  this codebase (reuse the math/transform-only discipline, not the
  literal classes — this is a different component).
- Reuse: `state.homeSelectedAccountId`, `computeBalance()`, `accounts`
  array order/`account.name` field.
- New design primitives required by this ticket: **one** —
  hidden-until-interaction auto-fading dot indicator (justified in the
  spec's decision 4; use existing fast/normal duration tokens).
- Mobile (<1024px) behavior: swipe/drag is the primary input; no arrow
  buttons; dots follow hidden-until-interaction rule.
- Desktop (>=1024px) behavior: always-visible arrow buttons are the
  primary input (no swipe available); dots still hidden-until-interaction,
  revealed by clicking an arrow or dot.

## Implementation guidance

- Likely files: `src/screens/home.js` (remove `accountSwitcherHtml()`,
  add carousel render + wiring), `styles.css` (hero card carousel/dots/
  arrows), `src/i18n.js` (new "Total balance" key).
- Likely functions/modules: `renderHome()` (`home.js:69-119`), the
  chip-click handler at `home.js:196-200` (replace with swipe/arrow/dot
  handlers doing the same `state.homeSelectedAccountId` assignment +
  `renderHome()` call).
- Existing pattern to reuse: `tx-row.js`'s drag tracking and 50%-width
  snap threshold (see `docs/specs/swipe-to-reveal-transaction-actions.md`
  Revisions 1-2) for the drag math; `docs/UX.md`'s Chips section
  precedent for why desktop needs an explicit always-visible affordance.
- Relevant tests: `e2e/type-selector-icon-color.spec.js` and any existing
  swipe-to-reveal e2e spec are useful references for how this codebase
  tests drag/gesture behavior and measures contrast/end-states in
  Playwright.
- Known invariants: `state.homeSelectedAccountId` is read by
  `markBillPaid()` too (`home.js:40-42`) — don't change its shape/values
  (`null` for all-accounts, else an account id), only how it gets set.
- Do not change: `computeBalance`, `monthTotal`, `pctDeltaLabel`,
  `sparklineSvg`, the Add screen's account picker, Settings' account rows.
- Escalate back to Claude if: the zero/one-account degenerate case turns
  out to need a real design decision rather than a reasonable default, or
  if reusing the swipe-to-reveal drag math doesn't actually fit a
  full-width horizontal carousel cleanly (different axis/constraints than
  a row reveal) and a materially different approach seems needed.

## Out of scope

- No persistence of the carousel's current page across reloads.
- No change to derived-data computation functions.
- No change to Add screen's account picker or Settings' account rows.
- Header/greeting (WI-020) and icon coloring (WI-022) are separate
  tickets.

**Confirmed defect (Claude review, pre-fix):** `styles.css` ~line 313-314
still has `.account-switcher-row` and its `::-webkit-scrollbar` rule —
dead CSS left over from the removed chip markup. Everything else in the
diff matched the acceptance criteria; `npm test` (173 passed), `npm run
test:e2e` (32 passed), build, and live-browser checks (mobile/desktop,
both themes, both languages, dot fade end-states, no-wraparound, reload

**Maintainer feedback (design revision):** dots read as too far apart and
don't visually connect old/new position when the page changes. See the
spec's new "Revision 1: sliding active-dot indicator + tighter spacing"
section — replace per-dot recolor with a single sliding indicator element
and tighten dot spacing, referencing iOS-style page indicators. Folded the
dead-CSS fix into the same follow-up pass.

Verified Revision 1 live in Chrome after the fix: indicator genuinely
slides (captured a mid-transition transform/opacity sample), state/
disabled-arrow logic correct in both directions. Unit 173/173 and build
passed; `npm run test:e2e` was blocked by Chromium being unavailable in
Codex's sandbox (known environment limitation, not a code failure).

**Maintainer feedback (Revision 2, visual-only):** no outline on the
dots, and spacing is too tight — see the spec's new "Revision 2: dot
visual style" section, with a reference image at
`E:\design\4df406d7a79e782db5d9cb4224ef1ddf.gif`. Filled dots (no
border), uniform size including under the indicator, wider pitch. Motion/
