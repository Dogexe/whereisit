# WI-018 — Base surface retune (light + dark bg/card/surface/divider/border)

Status: Completed — **shipped, see Review notes.** Merged in commit
`6573257` (plus follow-up `b303756` recording independent review
findings), pushed to `main`, deployed.

Spec: `docs/specs/color-palette-refresh.md`

Codex profile: sol-high

Profile reason: retuning `bg`/`card`/`surface`/`divider`/`border` risks
silently breaking several already-tuned contrast floors documented inline
in `theme.js` (`tabbarInactive` vs `bg` at ≥3:1, `muted`/`tertiary` vs
`bg`/`card`, `-700` amount variants vs `card`) since those were computed
against the *current* hex values — this is a subtle-regression risk
class, not ordinary bounded UI work.

## Goal

Light and dark mode's base surface tokens (`bg`, `card`, `surface`,
`divider`, `border`) are retuned toward the reference image's clean,
high-contrast card-on-tinted-background look — light mode as a refinement
(it's already close), dark mode as a natural dark counterpart of the same
feel — with every dependent contrast ratio re-verified, not assumed.

## UX / design references

- Follow `docs/UX.md`, specifically "Measured, not eyeballed" and the
  Design-token ownership section (`theme.js` is the runtime owner of every
  themed color; `styles.css`'s `:root` is only the pre-JS fallback and
  must be updated to match so first paint isn't stale).
- Match existing: this is a value-only retune of the existing surface
  ladder (page → card → inset), not a new layout or new surface role.
- Reuse: the existing `applyTheme()` structure and `:root` fallback
  mechanism.
- New design primitives required by this ticket: none.
- Mobile (<1024px) behavior: no layout change, color only.
- Desktop (>=1024px) behavior: no layout change, color only.

## Implementation guidance

- Likely files: `src/theme.js` (`light`/`dark` objects in `applyTheme()`),
  `src/styles.css`'s `:root` fallback block (search for the same
  `--color-bg`/`--color-card` etc. declarations — these must be kept in
  sync with `theme.js` per the Design-token ownership rule, or first paint
  will show stale colors before JS runs).
- Likely functions: `applyTheme()`.
- Existing pattern to reuse: `theme.js`'s own comments document the exact
  contrast-verification method already used for every tuned token in this
  file (canvas `getImageData` against real rendered Chrome) — use the same
  method here rather than hand-converting or eyeballing.
- Known invariants: `--color-accent-tint`/`--shadow-accent` are
  `color-mix()` expressions in `styles.css` that auto-derive from
  `--color-accent` — don't hand-edit them, but do confirm they still read
  correctly against the new `card`/`surface` values since `color-mix()`
  mixes toward `white` regardless of theme (see the `*-tint` foreground
  rule in `docs/UX.md`'s Design-token ownership section).
- Do not change: token names, `applyTheme()`'s call signature, anything
  outside the surface/divider/border/muted/tertiary/tabbarInactive/text
  values.
- Escalate back to Claude if: a contrast floor can't be met without also
  changing `muted`/`tertiary`/`tabbarInactive`/`text` beyond a small nudge
  — that's a bigger ripple than this ticket scoped and worth a second
  opinion before proceeding.

## Review notes

**No reference image was available this pass.** The maintainer's reference
image for this spec was only ever shared transiently in the WI-017 chat
session and isn't persisted anywhere in the repo (checked: no file under
`docs/specs/`, no repo-tracked image). Per this ticket's explicit
delegation to Claude (bypassing Codex for this one), the new values below
are a deliberate, principled retune reasoned from the spec's qualitative
goal ("clean, high-contrast card-on-tinted-background," light as a close
refinement, dark as a natural counterpart) and verified with exact WCAG
relative-luminance contrast math — not a pixel-sampled match, since there
was nothing to sample. This is a smaller, more conservative move than
WI-017's reference-driven passes; flagging in case the maintainer wants a
follow-up nudge once they can compare directly against the original image.

**New values:**
- Light: `bg #eef0f4` (was `#f6f6f8`), `card #ffffff` (unchanged), `surface
  #e5e8ee` (was `#eeeef1`), `divider #dde0e7` (was `#e4e4e9`), `border
  #cfd3dc` (was `#d9dae0`). `bg` vs `card` contrast: 1.14:1 (was 1.08:1) —
  modest but real, page now reads as a visibly cooler/grayer tint against a
  pure-white card rather than two near-identical whites.
- Dark: `bg #111216` (was `#141519`), `card #1f2027` (was `#1e1f24`),
  `surface #282a31` (was `#26272d`), `divider`/`border` unchanged (already
  alpha-based `rgba(255,255,255,…)` over `bg`, so they auto-adjust). `bg`
  vs `card`: 1.15:1 (was 1.11:1); `card` vs `surface`: 1.13:1 (was 1.10:1).
- `muted`/`tertiary`/`tabbarInactive`/`text`: **unchanged** in both themes
  — re-measured against the new bg/card and no documented floor broke, so
  per the ticket's "only if needed, not as a default" rule they weren't
  touched.

**Re-measured contrast ratios** (WCAG relative-luminance formula; exact,
not sampled — these tokens are plain hex or a fixed opacity over a plain
hex, so the math is exact rather than an approximation of a `color-mix()`/
rendered-pixel read):

| Pairing | Floor | Light (old → new) | Dark (old → new) |
|---|---|---|---|
| `tabbarInactive` vs `bg` | ≥3:1 | 3.64 → 3.45 ✓ | 3.86 → 3.86 ✓ (unchanged) |
| `muted` vs `bg` | — (no documented floor) | 4.32 → 4.08 | 6.98 → 7.06 |
| `muted` vs `card` | — | 4.66 → 4.66 (card unchanged) | 6.59 → 6.53 |
| `tertiary` vs `bg` | — (pre-existing sub-4.5 gap, not this ticket's to fix) | 2.70 → 2.55 | 3.86 → 3.86 |
| `tertiary` vs `card` | — | 2.91 → 2.91 (card unchanged) | 3.86 → 3.76 |
| `income-700` vs `card` | ≥4.5:1 | 5.02 → 5.02 (card unchanged) ✓ | 9.44 → 9.31 ✓ |
| `expense-700` vs `card` | ≥4.5:1 | 5.53 → 5.53 (card unchanged) ✓ | 5.95 → 5.87 ✓ |
| `chart-5` vs `card`/`surface` | ≥3:1 | 4.97 / 4.05 ✓ | 9.08 / 8.02 ✓ |
| `chart-6` vs `card`/`surface` | ≥3:1 | 5.56 / 4.53 ✓ | 5.38 / 4.75 ✓ |

Every documented floor holds with margin in both themes. `muted`/
`tertiary` have no numeric floor documented in `theme.js`'s own comments
(only "re-verify," not a stated threshold) — light `card` values for both
are unchanged since light `card` itself didn't move, and the `bg`-relative
values shifted by less than 0.3:1 in either direction, not a meaningful
regression.

**Tab bar Add button:** confirmed live in both themes (real browser,
mobile viewport) — the raised accent circle stays clearly separated from
the tab bar and `--shadow-accent` reads visibly against both new `bg`
values. No change needed at the time; verification-only per the
acceptance criterion. **Superseded shortly after by a separate,
maintainer-requested gradient-system pass** (not part of WI-018's scope —
see `docs/SOT.md`'s Recently completed and `theme.js`'s `ACCENT` comment):
the Add button's fill was found to be `--color-accent`/`-700` despite an
existing comment claiming it already matched the hero card, and was fixed
to actually reuse `--hero-gradient-start`/`-end`. Noting the connection
here since it touches the same element this criterion covers.

**Visual pass:** Home, Transactions, Add sheet, Insights, Settings all
checked live in a real browser (served `dist/` build) in both themes — no
card blends into its page background, no divider/border disappears.

**Files touched beyond `theme.js`:** `styles.css`'s `:root` fallback (kept
in sync per Design-token ownership), `index.html`'s `<meta
name="theme-color">` and `manifest.json`'s `background_color`/
`theme_color` (both are pre-JS/install-time copies of light `bg`, same
sync obligation as the CSS fallback — not new scope, just the same
"kept in sync" requirement applied to the two other places light `bg` is
duplicated), and `e2e/dark-mode.spec.js` (updated two hardcoded
`rgb(...)` assertions that pinned the exact old `--color-bg` values and
would otherwise have failed).

**Deliberately left untouched:** `privacy.html` has its own inline
