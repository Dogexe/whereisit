# WI-004 — Apple-style swipe actions on transaction rows

Status: Completed

Spec: `docs/specs/swipe-to-reveal-transaction-actions.md` (see "Revision 11:
clear every last sliver of row content once the bar is fully expanded" —
closes a small gap left by Revision 10, where `.tx-row-inner` stopped
translating exactly at the bar's own margin-inset edge instead of
continuing on to fully clear the row, leaving a sliver of row content (e.g.
trailing amount digits) visible even at full commit. Revisions 4-10 were
each implemented and live-verified in turn, then corrected/extended,
before any of this shipped to `main`.)

Codex profile: terra-medium

## Goal

Restyle transaction rows' Edit/Delete swipe actions into circular buttons
matching the category icon avatar's own size (40px), draggable from
anywhere on the row's content (not just the amount), sliding the row's
*entire* content (icon, category, note, amount) together as one block while
revealing the actions behind it — not just squeezing/moving the amount —
and add a full-swipe-to-delete gesture that deletes immediately (relying on
the existing Undo toast) once dragged past a commit threshold.

      — not stretched to the row's full height. Delete uses solid

      the maintainer live-checking Revision 5 — unchanged in this revision.)*

      threshold still governs drags that don't reach the full-swipe commit

- [x] `.tx-row-inner` (icon + category + note + amount — everything except

      avatar) visibly clips against `.tx-row-wrap`'s own `overflow: hidden`

      genuinely cut off, matching the reference screenshot. *(Confirmed

- [x] Dragging past `REVEAL` grows Delete from its resting circle into a

## Review notes

**From the Revision 4 pass (superseded shape, but the process findings still
apply — kept for record):**

Confirmed defect (fixed): Codex's first pass added a new e2e test
(`e2e/transactions-crud.spec.js`, "mobile full swipe...") that used
`page.mouse.move()`/`down()`/`up()` to simulate a touch drag. Because
Playwright's synthetic mouse events carry `pointerType: "mouse"`, moving
onto the row before dragging fired the row's *pre-existing, unrelated*
desktop hover-to-reveal handler, silently pre-opening the row before the
test's own drag began, exceeding the delete-commit threshold and deleting
the row unexpectedly — breaking every assertion after it. Root cause
confirmed by Claude independently (reran `npm run test:e2e`, reproduced the
mechanism with a standalone script, verified the underlying feature code was
correct via synthetic `pointerType: "touch"` events). Fixed by Codex in a
review-fix round using the same touch-PointerEvent technique; independently
reconfirmed by Claude: `npm test` 172/172, `npm run test:e2e` 17/17,
`npm run build` passing. **This same touch-PointerEvent technique should be
reused for Revision 5's own new/updated test**, for the same reason.

Optional suggestion (not adopted, by design, and still applicable): a
desktop mouse user gets the row pre-opened to `REVEAL` just by hovering
(pre-existing behavior, unrelated to this ticket), so committing a delete
from there needs less further drag than a fresh touch swipe would. Not a
silent trap (the button visibly grows the whole time) and consistent with
this app's existing act-then-undo convention — no action needed.

**Revision 5 amendment**: after live-checking the Revision 4 shape (full-
height 64px rectangles, amount-only drag handle), the maintainer asked for
two corrections — whole-row drag surface, and circular 40px buttons
matching the category icon instead of full-height rectangles. Interviewed
for the remaining specifics (circle color treatment stays solid, not the
category icons' own soft-tint style; full-swipe growth reads as
circle-to-pill-to-full-row-bar rather than a fixed-size circle). The spec
and this ticket were updated before any of the Revision 4 shape was
committed to `main`, so this is a plain amendment, not a regression fix.
Implemented by Codex and independently reconfirmed by Claude (`npm test`
172/172, `npm run test:e2e` 17/17, `npm run build` passing) — the maintainer
then live-checked the result and confirmed the circular buttons/colors and
whole-row drag surface are correct as built.

**Revision 6 amendment**: the maintainer supplied a reference screenshot (an
iOS Mail-style swipeable list) showing the entire row's content sliding and
clipping together, not just the amount — Revision 5 had kept Revision 3's
older "amount-area grows, lead content squeezes" mechanic even after moving
the drag handle to the whole row. This revision replaces that mechanic with
a genuine whole-row `transform: translateX()` slide, restructured so
`.tx-row-actions` sits behind `.tx-row-inner` as an independent sibling
rather than nested inside the part that used to grow — written up carefully
in the spec because this exact "content slides to reveal a panel behind it"
shape previously caused two real bugs (click-swallowing, icon clipping) the
first time this app tried it; see the spec's own explanation of why the new
construction avoids repeating that. Implemented by Codex and independently
reconfirmed by Claude (`npm test` 172/172, `npm run test:e2e` 17/17,
`npm run build` passing, plus a code-level check of the DOM/stacking-order
restructure and the e2e suite's real click-through assertion) — the
maintainer then live-checked the result and confirmed it.

**Revision 7 amendment**: the maintainer supplied a reference video (an
iPad Mail-style swipe) asking for one more polish pass — the action circles
should visibly pop in and grow as the row is first dragged open, not appear
at a fixed size. Claude watched the video frame-by-frame (via the `/watch`
skill) to confirm the exact motion before writing this revision: a small
dot grows to full circle size within the initial open drag, well before any
full-swipe/commit behavior. Purely additive on top of Revision 6's
confirmed-correct structure — no DOM/positioning changes expected, only new
scale-driven motion in `setRevealOffset`'s `0 → REVEAL` range. Implemented
by Codex (`npm test` 172/172, `npm run test:e2e` 17/17, `npm run build`
passing) — the maintainer live-checked it and called it "not bad," with one
refinement requested (Revision 8, below).

**Revision 8 amendment**: the maintainer's exact feedback: "each button
should behave separately and not show its full size until the row's edge
has moved past it — I don't want them to overlap, it doesn't feel premium."
Claude read Revision 7's actual shipped code (`setRevealOffset` in
`src/screens/tx-row.js`) to root-cause this precisely before writing the
fix, rather than guessing: both circles were scaling from one shared
`offset / REVEAL` progress value, so Edit — sitting further from the row's
edge than Delete, and so staying hidden behind `.tx-row-inner` for longer —
had its scale silently climbing the whole time it was still covered,
making it appear abruptly at a mismatched (already-large) size the instant
it was finally uncovered, instead of popping in small like Delete visibly
does. This is what read as "not premium," not a literal geometric overlap
between the two circles (their flex layout boxes never actually intersect).
The fix keys each circle's scale to its own reveal window instead of the
shared one — see the spec's Revision 8 section for the exact geometry.
Implemented by Codex (`npm test` 172/172, `npm run test:e2e` 17/17,
`npm run build` passing, derived each button's reveal window by measuring
its actual position rather than hardcoding, which is even more robust than
what was asked for) — the maintainer live-checked it and called it "almost
premium," with one more refinement requested (Revision 9, below).

**Revision 9 amendment**: the maintainer's exact feedback: "almost premium,
can you adjust the logic so icon only show full size when the space is
sufficient, idk technical term but you can ask." Rather than asking a
clarifying question on an inherently visual/hard-to-describe defect, Claude
verified it directly first: served a build, dragged a row open via
Playwright in small increments, and screenshotted the actions area zoomed
in at each step. The screenshots showed the precise defect plainly — a
circle mid-reveal renders as a flat-edge "D" shape (a disc sliced by a
straight line), not a small round dot — caused by Revision 8's scale
formula (a `0.3–0.4` floor, center-anchored) rendering the circle larger
than the space `.tx-row-inner`'s translate had actually uncovered at that
point, so `.tx-row-inner`'s own opaque covering (correctly, by design)
sliced off the excess. The fix removes the floor (raw `0 → 1` progress) and
anchors `transform-origin` at each circle's near edge instead of center, so
the circle's own edge and the reveal boundary always coincide exactly —
see the spec's Revision 9 section for the full derivation. Implemented by
Codex (`npm test` 172/172, `npm run test:e2e` 17/17, `npm run build`
passing, plus Codex's own visual verification) and independently
reconfirmed by Claude via the same zoomed-screenshot technique that caught
the original defect, at 11 offsets spanning both circles' reveal windows —
clean round dots throughout, no flat-edge artifact anywhere. This is the
first revision in this pass Claude verified as fully correct without any
outstanding maintainer feedback yet to confirm.

**Revision 10 amendment**: the maintainer's exact feedback: "when delete
button scale up it should follow the efficient space rule too, this one
somehow feel inconsistence, add a little space between row margin and
expanding button too." Claude root-caused the first part before writing
the fix: the `REVEAL → commit` bar-growth phase (`setRevealOffset`'s
`fullSwipe` branch) never adopted Revision 9's rule — it computes
width/height/right/top from an independent `progress` value with no
relationship to how far `.tx-row-inner` has actually translated, so at the
commit threshold the bar's formula resolves to the row's full width while
`.tx-row-inner` has only receded `65%` of the way — the same
render-more-than-revealed mismatch class Revision 9 fixed for the pop-in,
left unaddressed in this later phase. The second part (margin) is a plain
polish request, given a concrete value (`var(--space-xs)`, `8px`, reusing
an existing token) rather than inventing a new one. See the spec's
Revision 10 section for the full write-up and verification approach
(the same zoomed-screenshot technique that caught Revision 9's defect,
applied to this phase too). Implemented by Codex (`npm test` 172/172,
`npm run test:e2e` 17/17, `npm run build` passing) — the maintainer
live-checked it and called it "almost perfect," with one remaining sliver
(Revision 11, below).

**Revision 11 amendment**: the maintainer's exact feedback: "almost
perfect, just add a little bit space so there are no any content from the
row present when delete button fully expand." Claude verified this the
same way as Revision 9/10 before writing the fix — served a build, dragged
a row to near the commit threshold, screenshotted zoomed in — and could see
it directly: trailing amount-text digits (`"00"` of `"−฿55.00"`) still
visible next to the fully-expanded bar. Read Revision 10's actual shipped
formula (`Math.max(REVEAL, width + right)` for `.tx-row-inner`'s translate
target) to root-cause it precisely: at full progress this only reaches
`rowWidth - margin`, i.e. exactly `margin` px short of the row's true full
width — `.tx-row-inner` was made to stop at the bar's own near edge instead
of continuing on to fully clear the row underneath. The bar's own
margin-inset position (Revision 10's actual point) is correct and
unchanged; only `.tx-row-inner`'s translate target needs to go the rest of
the way. See the spec's Revision 11 section for the fix. Implemented by
Codex exactly as specified (`revealOffset = Math.max(REVEAL, width + right
+ fullSwipeMargin)`; `npm test` 172/172, `npm run test:e2e` 17/17,
`npm run build` passing) and independently reconfirmed by Claude via
zoomed screenshots of the full row at and past the commit threshold —
clean in both light and dark mode, no content sliver anywhere once fully
expanded.
