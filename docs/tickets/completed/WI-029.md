## Goal

`releaseOverlayHistory()` stops closing the overlay underneath the one being
released, so WI-028 can stack the Settings sub-page and the Manage sheet.

## The defect

`releaseOverlayHistory()` (`src/overlay-history.js:16-22`) pops its own entry
and then calls `history.back()`. The module's single `popstate` listener
(`:3-7`) pops **unconditionally**, so the traversal that release just caused
consumes the *next* entry down and fires its `onPop`. Reproduced against the
merged module with stubbed `window`/`history`:

```
push("settings-subpage", …); push("settings-manage", …);
releaseOverlayHistory("settings-manage");
-> fired: [ 'subpage onPop' ]   history entries: 1
```

Both entries are gone and the lower overlay closed itself. This is latent, not
live: none of the five WI-026/WI-027 consumers can be open at the same time
(WI-027's review notes verify the no-co-open claim), so nothing stacks two
entries today. WI-028 is the first ticket that does, which is why it escalated.

The spec's "Release" bullet and its decision 2 both say the resulting pop
"finds nothing" — true only for a stack of one. Both are corrected in the same
change as this ticket, along with WI-028's inherited copy of the claim.

## Implementation guidance

- **Likely files:** `src/overlay-history.js` (22 lines — read it first, it is
  shorter than this section), a new `tests/overlay-history.test.js`, and the
  doc corrections listed under Verification.
- **Suggested shape** — suppress exactly the pops release causes:

  ```js
  let suppressedPops = 0;

  window.addEventListener("popstate", () => {
    if (suppressedPops > 0) { suppressedPops--; return; }
    const entry = overlayStack.pop();
    if (!entry) return;
    entry.onPop();
  });

  // in releaseOverlayHistory, replacing the bare history.back():
  overlayStack.pop();
  suppressedPops++;
  history.back();
  ```

  Deviate only with a reason recorded in Review notes.
- **A counter, not a boolean.** Same size, correct on the edge case a boolean
  gets wrong: two releases in one task queue two traversals, and a boolean would
  swallow one popstate and let the other close a live overlay.
- **`popstate` is asynchronous.** The suppression cannot be a call-stack guard or
  a `try/finally` — `history.back()` returns immediately and the event arrives on
  a later task. That is exactly why a module-level counter is the shape, and why
  the unit test's stubbed `back()` must invoke the listener the way the real one
  does.
- **Reason about a release whose `back()` produces no `popstate`.** If that can
  happen the counter never drains and the user's next Back is swallowed. Every
  entry release drops was pushed by `pushOverlayHistory`, so the traversal should
  always have somewhere to go — confirm that rather than assume it, and say so in
  Review notes.
- **Do not dispatch on `event.state` instead.** That was considered and rejected
  in the spec's decision 1: `main.js:73`/`:109` can `replaceState` the tag away,
  so the stack is the source of truth and the tag is identification only.
- **Unit test shape.** The module registers its `popstate` listener at import
  time, so the stubs must be installed on `globalThis` *before* a dynamic
  `import()` of it — the rest of `tests/` imports statically, so this one file
  will look different on purpose; say why in a comment. A minimal
  `window.addEventListener` that captures the listener, plus a `history` with
  `pushState`/`back()` that invokes it, is enough.
- **The unit test is the real gate here, and that is deliberate.** No UI path can
  stack two entries until WI-028 ships, so e2e cannot reach the defect.
  `npm run test:e2e` covers the other half — that the five shipped sheets did not
  regress.
- **Do not change:** the exported API, the `{ overlay: key }` tag, the
  duplicate-key no-op, any consumer, or `settings.js`'s own `popstate` listener
  (WI-028 deletes that one, not this ticket).
- **Escalate back to Claude if:**
  - the fix appears to require an API change or any consumer edit;
  - a released `history.back()` can fail to produce a `popstate`, leaving the
    counter stuck;
  - browsers coalesce two queued traversals into a single `popstate`, which would
    make the counter over-suppress.

### Confirmed defects

- **The defect the ticket describes, reproduced and fixed.** The new
  `tests/overlay-history.test.js` was run against `HEAD:src/overlay-history.js`
  as well as the fix. Against the pre-fix module exactly one test fails —
  "releasing the top entry leaves the one below it open (WI-029)" — and it fails
  in the documented way: `A`'s `onPop` fires and its history entry is gone.
  Against the fix all eight pass. The other seven passing on both sides is
  intentional: they are the over-suppression guards, and their job is to be
  green before *and* after.

### Escalation conditions, checked rather than assumed

- **Can a released `history.back()` fail to produce a `popstate`, sticking the
  counter?** No. Every entry the stack holds was put there by
  `pushOverlayHistory()`, which calls `history.pushState()` in the same
  statement, so at release time there is always at least one session-history
  entry behind the current one and the traversal always has somewhere to go.
  The only other history calls in the app are `main.js:73` and `:109`, and both
  are `replaceState` — they overwrite the current entry's state without
  changing the entry count, so they cannot strand the counter either. No
  escalation.
- **Could browsers coalesce two queued traversals into one `popstate`, making
  the counter over-suppress?** Not reachable today, and not worth designing
  around yet. Two releases in the same task is the only way to queue two
  traversals, and no such path exists: each of the six consumers releases only
  its own key, and `WI-027`'s review notes established that no two of the five
  sheets can co-open. `WI-028` is the first ticket that can stack two entries,
  and even there the two are released by separate user gestures. Flagging it
  rather than hiding it: if a future consumer ever releases two entries
  synchronously, that is the one path where a real browser could diverge from
  the unit test's stub, and it should be checked live at that point.

### Deviations from the ticket's guidance

- The ticket predicted the new test file "will look different on purpose"
  because the rest of `tests/` imports statically. That is not quite true —
  `tests/applock.test.js` already installs a `globalThis.window` stub before a
  dynamic `import()`, for the same load-time-global reason. The comment in the
  new file points at that precedent instead of explaining the pattern from
  scratch.
