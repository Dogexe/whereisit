# WI-026 — Shared overlay-history owner, adopted by the Add sheet only

Status: Completed

Spec: `docs/specs/back-button-dismisses-overlays.md`

Codex profile: sol-high

Profile reason: browser history and `popstate` re-entrancy — `history.back()`
is asynchronous and this code has to coexist with a second, deliberately
untouched `popstate` listener in `settings.js`; the failure mode (a Back press
that closes two things, or none) is easy to write and hard to see.

Risk tier: Medium

## Goal

With the Add sheet open on mobile, browser/hardware Back closes the sheet and
stays in the app — and every existing way of closing the sheet leaves no stale
history entry behind.

## Acceptance criteria

- [x] A new module `src/overlay-history.js` exports
      `pushOverlayHistory(key, onPop)` and `releaseOverlayHistory(key)`, and
      registers exactly one module-level `popstate` listener.
- [x] `pushOverlayHistory` pushes `history.pushState({ overlay: key }, "")` —
      **same URL**, no third argument — and records `{ key, onPop }` on a
      module-level stack.
- [x] Pushing a key already on the stack is a no-op (no second entry).
- [x] On `popstate`, the top stack entry is popped and its `onPop()` called.
      An **empty stack is ignored**, so `settings.js`'s own listener continues
      to handle Settings sub-page pops exactly as it does today.
- [x] Dispatch is driven by the module's stack, **not** by `event.state`.
      `event.state` is the state being landed on, not the one being left; and
      `main.js:73`/`main.js:109` both `replaceState(null, …)` and can null the
      tag out. The tag is for identification only.
- [x] `releaseOverlayHistory(key)` removes the entry from the stack **before**
      calling `history.back()`, so the resulting `popstate` does not re-run
      `onPop`. It acts only when `key` is the **top** entry; otherwise it
      returns `false` and does nothing.
- [x] `openAddSheet()` (`add.js:578`) pushes an entry; `closeAddSheet()`
      (`add.js:583`) releases it. No other call site changes.
- [x] Back with the Add sheet open closes the sheet, keeps the URL, and stays
      in the app (the audit recorded `goBack()` landing on `about:blank`).
- [x] Cancel, backdrop tap, Escape, swipe-down-to-dismiss, and a successful
      save each release the entry, so a later Back is not swallowed. Because
      `history.back()` retains the released entry as a *forward* entry,
      `history.length` does not return to its pre-open value; coverage asserts
      the restored base state and a stable, non-accumulating length instead.
      (Corrected during review — the original wording was unachievable.)
- [x] Opening and closing the sheet repeatedly does not accumulate entries.
- [x] `src/screens/settings.js` is **not** modified, and
      `e2e/nav.spec.js:73-108` (Settings sub-page history) still passes
      unchanged.
- [x] `setTab()` still pushes no history — tab switches are deliberately
      unchanged.
- [x] No new CSS, class, `STRINGS` key, icon, or visible control.
- [x] Existing related behavior remains unchanged.

## UX / design references

- Follow `docs/UX.md`.
- Match existing: `openSettingsSubPage`/`closeSettingsSubPage` and their
  `popstate` listener (`settings.js:158-174`) — same same-URL `pushState`, same
  "closes only through `history.back()`" discipline, generalized into a module.
- Reuse: the Add sheet's existing `dismiss`/`closeAddSheet` funnel
  (`add.js:568-588`). Back must become a new *caller* of the existing close,
  not a new close path.
- New design primitives required by this ticket: **none.** Nothing visual
  changes. Any CSS, class, string, or icon in the diff is a defect.
- Mobile (<1024px) behavior: Back closes the open Add sheet; otherwise
  unchanged.
- Desktop (≥1024px) behavior: unchanged — the Add sheet does not exist there
  (every `openAddSheet()` call site guards with `!isDesktopShell()`).

## Implementation guidance

- **Likely files:** new `src/overlay-history.js`; `src/screens/add.js`
  (`openAddSheet` at 578, `closeAddSheet` at 583); `e2e/nav.spec.js` (new
  coverage). Nothing else.
- **Existing pattern to reuse:** `settings.js:158-174` is the working
  reference implementation of this idea for one surface — read it first. Note
  in particular that it never closes the sub-page directly; `history.back()` is
  the only path, and the `popstate` handler is the only place that clears
  state. This ticket generalizes that shape but *inverts* one detail: a sheet's
  UI dismissal already closes the sheet itself, so the release call must
  de-register before `history.back()` rather than relying on the pop.
- **`closeAddSheet` is already the single funnel** for every dismissal —
  Cancel and backdrop tap and swipe-down all route through `dismiss`
  (`add.js:568-572`), Escape through the module-level keydown listener
  (`add.js:591-593`), and save through `onSaved` (`add.js:574`). One
  `releaseOverlayHistory` call inside `closeAddSheet` covers all five. Do not
  add per-path calls.
- **The re-entrancy guard is an ordering requirement, not a flag.** Pop the
  stack entry first, then `history.back()`. `onPop` for the Add sheet is
  `closeAddSheet` itself, which calls `releaseOverlayHistory` again — that
  second call must find the entry already gone and no-op, or Back will pop
  twice and exit the app.
- **`history.back()` is asynchronous.** Do not write code that assumes the
  resulting `popstate` has already fired when `releaseOverlayHistory` returns.
- **Known invariants:**
  - `settings.js:170`'s listener guards only on
    `SETTINGS_SUB_PAGE_IDS.has(state.settingsSubPage)`, not on `event.state`.
    Release 1 is safe *because* the Add sheet can never be open while a
    Settings sub-page is: `e2e/nav.spec.js:90` asserts the tab bar is hidden
    once a sub-page opens, and the tab bar holds the only mobile Add entry
    point reachable from Settings. Do not weaken that test.
  - Sheet-open flags are UI-only and not persisted (`state.js:87-111`), so a
    reload starts with an empty stack and no open sheet — consistent by
    construction. No restore path to handle.
  - `history.pushState(state, "")` with no third argument leaves the URL
    untouched; every e2e navigation assertion and the PWA start URL depend on
    that.
- **Relevant tests:**
  - `e2e/nav.spec.js:73-108` — the existing Settings history round trip. It is
    both the model to copy (it already asserts `history.length + 1` and an
    unchanged URL) and the regression guard that `settings.js` still works.
  - `e2e/nav.spec.js:66-71` — asserts the Add sheet opens from the tab bar;
    should keep passing untouched.
  - `tests/` — DOM-less `node:test`; nothing here is unit-testable without
    injecting a fake history object, which the spec rejects. Expect no unit
    test to change.
- **Do not change:** `src/screens/settings.js`, `router.js`'s `setTab`,
  any sheet other than Add, the Add sheet's markup or dismissal semantics
  (silent discard is deliberate, `add.js:565-568`), or any URL/route.
- **Escalate back to Claude if:**
  - a Back press turns out to be able to reach the Add sheet and a Settings
    sub-page at the same time (that would invalidate the whole
    release-1-is-safe premise);
  - making Back work appears to require touching `settings.js`, `setTab()`, or
    the URL;
  - the double-`releaseOverlayHistory` no-op cannot be made reliable by
    ordering alone;
  - the Manage sheet or any Release 2 sheet seems to need adopting now to make
    this coherent — it does not, and batching is explicitly ruled out by
    `docs/ROADMAP.md`.

## Review notes

### Confirmed defects

1. **The deliberate deviation from the spec's verification plan was not
   recorded in the repository.** `workflows/ship-feature.md` step 6 requires
   updating the relevant spec with what actually shipped versus what was
   planned. The spec (and this ticket) called for `history.length` to return to
   its pre-open value after a non-Back dismissal, which `history.back()` cannot
   do — it retains the released entry as a forward entry, so the length stays
   at N+1. The implementation and its tests correctly assert a restored base
   state and a stable, non-accumulating length instead, satisfying the spec's
   real intent ("a later Back is not swallowed"), but that reasoning existed
   only in the handoff message. **Resolved:** spec verification plan corrected
   at `back-button-dismisses-overlays.md:260`, and the acceptance criterion and
   verification wording above corrected to match. Docs-only; no code, test, or
   build change.

### Optional suggestions

Kept separate from the defect above. None block this ticket.

1. **Back is the only dismissal path that skips `resetForm()`.** `onPop` is
   `closeAddSheet`, while Cancel, backdrop tap, swipe-down, and Escape route
   through `dismiss = () => { resetForm(); closeAddSheet(); }` (`add.js:569`).
   Verified live to be currently harmless — Back out of an edit sheet, then
   reopen from the tab bar, yields a clean Add sheet with an empty note —
   because all four fresh-open call sites (`main.js:87`, `home.js:25`,
   `transactions.js:17`) call `resetForm()` first. It does leave
   `state.editingId` set while the sheet is closed, a state no other dismissal
   produces. *Declined by Codex:* the accepted acceptance criterion names
   `closeAddSheet` as the releasing function, and the transient state is
   harmless. Revisit if a future entry point opens the sheet without resetting.
2. **Coverage versus the five named dismissal paths.** The e2e drives Cancel
   and save; backdrop tap, Escape, and swipe-down funnel through the same
   `closeAddSheet`, so they are covered by construction rather than by three
   more tests. *Declined:* no confirmed defect.
3. **Browser Forward onto a released entry** leaves `history.state.overlay` set
   against an empty stack, so the next Back is a visual no-op. `settings.js`
   behaves identically today (its listener guards on `state.settingsSubPage`,
   null after close). Pre-existing and not introduced here. *Declined:* worth
   at most a spec line before Release 2 generalizes the module further.
