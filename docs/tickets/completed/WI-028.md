## Goal

Settings' mobile sub-page and the Manage sheet both run on the shared overlay
history owner, leaving exactly one `popstate` listener in the app — which is
what actually retires D3 rather than routing around it.

## Acceptance criteria

- [x] `openSettingsSubPage` (`settings.js:158`) pushes through
      `src/overlay-history.js` instead of calling `history.pushState` directly,
      keeping its existing `!isDesktopShell()` guard and its same-URL push.
- [x] `closeSettingsSubPage` (`settings.js:164`) **clears
      `state.settingsSubPage` and re-renders itself**, then releases its
      history entry. It no longer relies on `popstate` to do the clearing (see
      Implementation guidance — this inversion is the trap in this ticket).
- [x] `settings.js`'s own `popstate` listener (`:170-174`) is **deleted**. The
      app has exactly one `popstate` listener afterward.
- [x] The Manage sheet pushes on its existing open transition
      (`settings.js:127`) and releases on its existing close transition
      (`settings.js:83`). No new open/close detection mechanism is introduced.
- [x] With a Settings sub-page open and the Manage sheet open on top: the first
      Back closes only the sheet, the second returns to the Settings root, and
      the third leaves Settings — in that order, with the sub-page never
      closing early.
- [x] Closing the Manage sheet by any existing route — close button, backdrop
      tap, Escape (`settings.js:129-133`), swipe-down, or a successful save
      (which clears the edit id and re-renders into the close transition) —
      leaves the sub-page open and its history entry intact.
- [x] A bill-reminder notification deep link (`main.js:68-74`) still lands on
      the bill's edit form, and Back from there behaves as above, despite the
      `replaceState(null, …)` that immediately follows the pushes.
- [x] Switching tabs away from Settings while a sub-page is open
      (`main.js:90`) still closes the sub-page and leaves no stale entry.
- [x] Desktop (≥1024px) still pushes nothing for either surface, and the
      desktop section nav (`settings.js:429`) is untouched.
- [x] `docs/ARCHITECTURE.md:71-73` is updated — "A Settings sub-page closes
      only through `history.back()`; the `popstate` handler in `settings.js` is
      the single place that clears the field and re-renders" stops being true
      in this ticket, and a stale sentence there actively misleads.
- [x] `e2e/nav.spec.js:124-159` still passes **unchanged** — same URL, same
      `history.length + 1`, same Back behavior. The whole point is that this
      migration is invisible from the outside.
- [x] WI-026's and WI-027's sheet behavior is unchanged.
- [x] No new CSS, class, `STRINGS` key, icon, or visible control.

## UX / design references

- Follow `docs/UX.md`.
- Match existing: WI-026/WI-027's adoption shape. The sub-page is not a sheet,
  but it becomes the same kind of stack entry.
- Reuse: `renderManageSheet()`'s existing open/close transition detection
  (`settings.js:83` and `:127`), which already arms and disarms the focus trap
  at exactly the two moments the history entry needs pushing and releasing.
- New design primitives required by this ticket: **none.** Nothing visual
  changes; this is a mechanism swap behind identical behavior.
- Mobile (<1024px) behavior: as today, plus Back now closes the Manage sheet
  before the sub-page.
- Desktop (≥1024px) behavior: unchanged — neither surface is history-backed
  there.

## Implementation guidance

- **Likely files:** `src/screens/settings.js` (only real code file),
  `docs/ARCHITECTURE.md`, e2e coverage. `main.js` should need no change; if it
  does, say so in review notes.
- **The trap — read this before writing anything.** Today
  `closeSettingsSubPage()` *only* calls `history.back()`; it never clears
  `state.settingsSubPage`. The `popstate` listener at `:172` is the sole
  clearer, which `docs/ARCHITECTURE.md:71-73` documents as deliberate. But the
  shared owner removes an entry from its stack *before* calling
  `history.back()` (confirmed in the shipped `overlay-history.js:26-28`), so
  the resulting pop does not re-close the entry just released — and, since
  `WI-029`, is swallowed outright by the `suppressedPops` counter, so it does
  not reach the entry below it either. Port the
  function unchanged and nothing clears the field: the sub-page stays open in
  state while its history entry disappears. `closeSettingsSubPage` must take
  over the clearing and re-render, exactly as `closeAddSheet()` closes its own
  sheet. Verify this deliberately — it fails silently, and only on the
  button-and-tab-switch paths, not on Back.
- **The Manage sheet needs no new detection.** `renderManageSheet()`
  (`settings.js:78-128`) already computes both edges to manage its focus trap:
  close at `:83`, open at `:127`. Push and release there. Note the close edge
  also fires when `isDesktopShell()` becomes true — a resize across the
  breakpoint with the sheet open will release the entry, which is correct, but
  confirm it does not throw when there is no entry to release.
- **`state.manageSheetOpen` is load-bearing elsewhere:** `sync.js:516`'s
  `hasLiveInputRisk()` reads it to suppress re-renders over live input. Do not
  repurpose or remove the flag.
- **The deep-link path pushes twice in one tick without a gesture**
  (`main.js:68-74`): `openSettingsSubPage("bills")` pushes, then
  `state.billEditId = …` plus `renderScreen()` pushes the Manage sheet, then
  `replaceState(null, "", pathname)` nulls the tag on the entry just pushed.
  Stack-based dispatch survives that; tag-based dispatch would not. This is the
  single best end-to-end test of the whole design — write it.
- **`closeSettingsSubPage`'s return value** is currently `false` on desktop or
  with no sub-page open, and `true` otherwise. Its only caller (`main.js:90`)
  ignores it. Keep the contract rather than changing it for no reason.
- **Behavior change worth noticing, not fixing:** today, `main.js:90`'s
  tab-switch calls `closeSettingsSubPage()` → `history.back()` → a late
  `popstate` that clears the field and calls `renderScreen()` *after* the new
  tab already rendered — a redundant re-render. After this change that late pop
  is consumed by `WI-029`'s `suppressedPops` counter before the listener body
  runs, and `settings.js`'s own listener is gone anyway, so nothing happens.
  That is strictly better; just don't mistake the missing second render for a
  regression.
- **The one path `WI-029` asks you to watch: two releases in the same task.**
  `WI-029`'s counter assumes each `history.back()` it causes produces its own
  `popstate`. Two releases queued in one task queue two traversals, and its
  review notes record that as unreachable *at the time* — which this ticket is
  the first to change, since it is the first to put two entries on the stack.
  Reasoned through and still unreachable, but confirm rather than assume:
  `main.js:90`'s tab switch is the candidate, and it is blocked by the same
  thing that kept the five shipped sheets from co-opening —
  `.filter-sheet-backdrop`'s `z-index: 50` (`styles.css:553`) covers the tab
  bar's `30`, so a tab cannot be tapped while the Manage sheet is open. Note
  also the ordering if a path is ever found: `main.js:90` releases the sub-page
  *first*, and the sub-page is the lower entry, so
  `releaseOverlayHistory("settings-subpage")` would return `false` and leave a
  stale entry rather than misbehaving loudly. Escalate if you find any route
  that releases both in one task.
- **Relevant tests:**
  - `e2e/nav.spec.js:124-159` — the existing round trip. It must pass
    **unchanged**; needing to edit it means behavior moved, which this ticket
    does not permit.
  - `e2e/manage-row-swipe.spec.js` — drives the Manage sheet's forms; the
    natural place for the stacked Back assertions.
  - `tests/` — nothing unit-testable here.
- **Do not change:** the sub-page's URL behavior (still same-URL), the desktop
  section nav (`settings.js:429`), `router.js`'s `setTab`, `state.manageSheetOpen`'s
  meaning, or `src/overlay-history.js`'s API (an API change here is an
  escalation).
- **Escalate back to Claude if:**
  - the sub-page and Manage sheet can be popped out of order, or one Back
    closes both;
  - `renderManageSheet`'s two transition points turn out not to be reliable
    open/close edges in some path;
  - `main.js` needs changing to make the deep link work;
  - `e2e/nav.spec.js:124-159` needs editing to pass;
  - the migration seems to require keeping `settings.js`'s `popstate` listener.

## Review notes

Implemented by Codex (`gpt-5.6-sol`, high effort) on branch
`wi-028/settings-subpage-and-manage-sheet`, off `WI-029`'s. Reviewed by Claude
read-only before any edit, per `CLAUDE.md`. Two commits: `ed96c7d` for the
migration, `0ac6a0b` for the one review finding below.

The migration went in at the seams the ticket named, with no consumer or API
change: `openSettingsSubPage()` pushes through the shared owner,
`closeSettingsSubPage()` now clears `state.settingsSubPage` and re-renders
before releasing, `settings.js`'s own `popstate` listener is gone, and the
Manage sheet rides `renderManageSheet()`'s existing focus-trap transitions.
`grep` confirms `src/` now has exactly one `popstate` listener, which was the
point of the release.

**One mechanism is load-bearing and non-obvious, so it is recorded here rather
than left to be rediscovered.** `closeSettingsSubPage` is registered as its own
entry's `onPop` *and* itself calls `releaseOverlayHistory`. That is re-entrant
by construction, and it is safe only because the owner pops the stack *before*
invoking `onPop`: the nested release then finds a different key on top and
returns `false`. The Manage sheet's `dismiss` closure self-cancels the same
way. Anything that later reorders `overlay-history.js`'s listener — popping
after the callback instead of before — breaks both surfaces silently.

### Confirmed defects

- **The `createBudget` fixture synthesized history state (Claude review,
  resolved by Codex in `0ac6a0b`).** The first implementation added, to
  `e2e/helpers.js`'s `createBudget` under 1024px only, a
  `history.pushState(history.state, "")` described in-comment as replacing a
  "fixture-only forward slot". It was load-bearing, not cosmetic: isolating it
  — removing that block while keeping the legitimate
  `waitForMobileManageSheetRelease` async fix — failed the protected
  `e2e/nav.spec.js:146` with `Expected: 5, Received: 4`. It was therefore the
  mechanism by which `nav.spec.js:124-159` "passed unchanged", which sits
  directly against this ticket's escalation trigger about that test; editing
  the shared fixture the test depends on, to the same effect, in a file this
  ticket does not list under Likely files, should have been escalated. It was
  not, and the Review notes were left as the empty template.
  The underlying behavior is **not** an application regression: a released
  entry leaving a forward slot is inherent to `releaseOverlayHistory()`'s
  `history.back()` design and was already true of the five sheets shipped in
  `WI-026`/`WI-027`. What was new is that `createBudget` began tripping it
  before `nav.spec` took its own baseline measurement — a fixture-ordering
  artifact.
  Codex reproduced the measurement independently before acting, then replaced
  the injection: mobile `createBudget` now seeds through the real
  desktop-inline form, restores the viewport, and reopens the mobile Budgets
  section, so no synthetic history state is created and callers get a genuine
  top-of-history baseline. Confirmed on review that this loses no coverage —
  the mobile Manage-sheet save is exercised deliberately at
  `e2e/overlay-history.spec.js:169-172`, alongside the other five non-Back
  dismissal routes.

- **Blocked before implementation (Codex, sol-high, 2026-09-09).** The shipped
  `src/overlay-history.js` cannot keep a lower stack entry alive when the top
  entry is released by a non-Back dismissal. `releaseOverlayHistory()` pops its
  own entry and then calls `history.back()`; the module's single `popstate`
  listener pops unconditionally, so it consumes the *next* entry down and fires
  its `onPop`. With `[settings-subpage, settings-manage]`, every non-Back close
  of the Manage sheet — close button, backdrop, Escape, swipe-down, save —
  would also close the sub-page, violating the acceptance criterion that those
  routes leave the sub-page and its entry intact. Reproduced against the merged
  module with a direct harness: releasing `settings-manage` returns `true` and
  invokes the sub-page's `onPop` immediately.
  This is latent, not live: the five WI-026/WI-027 consumers never stack two
  entries, so WI-028 is the first ticket to expose it. The ticket's premise that
  "the resulting pop really is a no-op by design" holds only for a stack of one.
  Fixing it means making `releaseOverlayHistory()`'s own pop self-cancelling
  (internal change to `overlay-history.js`, no API change) — out of WI-028's
  stated scope, hence the escalation. No repository changes were made.
