# WI-005 — Apple-style swipe actions on Settings' Manage rows

Status: Completed

Spec: `docs/specs/settings-manage-swipe-and-sheet.md` (see "Revision:
Apple-style colored full-height actions + full-swipe-to-delete")

Codex profile: terra-medium

> **Ticket refreshed against shipped WI-004.** This ticket's original
> acceptance criteria were written before WI-004 landed and encoded an
> early draft of it — full-height rounded rectangles at 64px per
> button. WI-004 then went through eleven live-checked revisions and
> shipped something different: **40px circular buttons that match the
> category icon avatar**, with a pop-in/grow animation. The criteria
> below are re-derived from the actual shipped implementation
> (`src/screens/tx-row.js`, `styles.css`'s `.tx-row-actions` block), not
> from the draft. **`src/screens/tx-row.js` and its CSS are the
> reference — where this ticket's prose and that code disagree, the code
> is right; say so in review rather than following the prose.**

## Goal

Apply the same Apple-style colored full-height action buttons and
full-swipe-to-delete gesture from WI-004 (transaction rows) to Settings'
Manage rows (Budgets, Bills, Categories, Accounts, Goals), adapted for
their variable action count (2 or 3 buttons) and whole-row drag surface.

## Acceptance criteria

- [ ] `manageSwipeWrapHtml`'s reveal width formula changes from
      `20 + actionCount * 34` to WI-004's actual per-button math:
      12px leading padding + 40px per button + 4px between buttons,
      i.e. `12 + actionCount * 40 + (actionCount - 1) * 4`. This yields
      **96px for 2 buttons**, matching `tx-row.js`'s shipped
      `REVEAL = 96` exactly, and 140px for Accounts' 3 buttons. The
      existing code comment claiming tx-row.js implies "88px (n=2)" is
      stale and must be corrected with this change.
- [ ] Every action button renders as a **40px circle**
      (`width: 40px; height: 40px; min-width: 40px; padding: 0;
      border-radius: 20px; box-shadow: none`), matching the category
      icon avatar — the same values `styles.css`'s
      `.tx-row-actions .tx-swipe-action` rule already uses. Full-height
      rounded rectangles are **not** what WI-004 shipped; do not
      introduce them.
- [ ] Buttons use WI-004's pop-in/grow reveal: `transform: scale(0)`
      with `transform-origin: right center`, grown to `scale(1)` as the
      drag passes each button's own reveal span, with the transition
      suppressed while `.dragging`. Mirror `tx-row.js`'s existing
      per-button `data-reveal-start` / `data-reveal-end` progress
      approach rather than inventing a second mechanism.
- [ ] Delete uses `var(--color-expense)` background + white icon. Edit and
      Accounts' Archive/Unarchive both use `var(--color-border)` background +
      `var(--color-text)` icon (differentiated only by their own icon). No
      new color values/tokens introduced. (These three already match
      shipped WI-004 — `.tx-swipe-delete` / `.tx-swipe-edit`.)
- [ ] The committed full-swipe state matches WI-004's: an added
      `full-swipe` class collapses the actions group to `inset: 0;
      width: auto; gap: 0; padding: 0`, fades Edit out
      (`opacity: 0; pointer-events: none`), and promotes Delete to
      `position: absolute; z-index: 1`.
- [ ] **Leftward drag is linear, with no rubber-band damping**, matching
      `tx-row.js`'s `raw < 0 ? -Math.sqrt(-raw) * 2 : raw` — resistance
      applies only to over-closing (the negative direction). The current
      `else if (raw > reveal) clamped = reveal + Math.sqrt(raw - reveal) * 2`
      branch damps exactly the range that is now the full-swipe grow
      regime, so the Delete pill cannot physically reach full width:
      measured on a 314px Accounts row, dragging to the left screen edge
      grows it to only 154px of its 298px target, and reaching 298px
      would need ~2342px of travel. Delete that branch. The commit
      decision already uses the raw offset and must keep doing so.
- [ ] In the committed full-swipe state, **every** non-Delete action is
      hidden, not just Edit — this must hold for Accounts' 3-button case
      (Edit *and* Archive/Unarchive), not only the 2-button sections.
- [ ] Full-swipe-to-delete: dragging past 65% of `.manage-row-wrap`'s own
      width and releasing there calls the existing delete flow for that
      section immediately (existing Undo toast, no new confirmation).
      65% is `tx-row.js`'s shipped `DELETE_COMMIT_RATIO = 0.65`; reuse
      that value rather than a new constant.
      Applies correctly regardless of button count (2 for
      Budgets/Bills/Categories/Goals, 3 for Accounts) — Delete is always
      the last/rightmost action.
- [ ] Releasing between the reveal point and the 65% commit threshold snaps
      back to fully open (not closed, not deleted).
- [ ] Goals: only Edit/Delete are affected (2-button case) — Contribute
      stays outside the swipe wrapper, unchanged.
- [ ] Icon-only buttons, no visible text labels added.
- [ ] **The whole row content slides as one unit**, exactly as
      transaction rows do — the content must not squeeze, truncate or
      reflow as the actions appear. Adopt `tx-row.js`'s actual shipped
      mechanism: the actions layer is absolutely positioned behind the
      content (`position: absolute; inset-block: 0; right: 0;
      z-index: 0`), and the content element translates left over it
      (`transform: translateX(-offset)`, `position: relative;
      z-index: 1`, with an opaque `background: var(--color-card)` so
      the actions never show through). Today's mechanism — growing
      `.manage-row-actions-group`'s width from 0 while the flex content
      column absorbs the loss by truncating its own text — is what
      produces the squeeze, and it is replaced by this.
- [ ] The module's leading comment in `manage-row-swipe.js` is
      corrected as part of this. It currently claims the reveal is done
      "the same proven way tx-row.js already validated: growing a real
      flex box's width, never an overlaying positioned layer" — that
      description no longer matches `tx-row.js`, which does use a
      positioned layer beneath a translating content element. Leaving a
      comment that misdescribes the reference implementation is how this
      ticket went stale in the first place.
- [ ] Goals' card-shaped variant (`goal-card-top-content`, which passes
      its own `contentClass`/`wrapClass`) slides correctly too, with
      Contribute still outside the swipe wrapper and unaffected.
- [ ] Desktop (1024px+) Settings layout is pixel-unchanged for every
      section (always-visible icons, inline forms — untouched).
- [ ] Light and dark mode both render correctly.
