# WI-007 — Fix Add sheet content ghosting above the header when the keyboard opens

Status: Completed

Spec: `docs/specs/add-sheet-keyboard-open-ghosting.md`

Codex profile: sol-highest

Profile reason: escalated from `sol-high` after attempt 1 shipped and was
disproven on the real device (see Review notes below) — this is now
literally `AGENTS.md`'s "a task where `sol-high` has already failed to
produce a reliable solution" criterion, not merely a large task.

## Goal

Eliminate the transient (~1-1.5s) glitch where the Add sheet's Type field
content renders above the sheet's own rounded top edge and above the
sticky header, visible while the on-screen keyboard is opening after the
Note field is focused.

## Approach (attempt 2 — decided with the maintainer)

`contain: paint` is ruled out on-device (see spec's Investigation). The
remaining suspect is that `.filter-sheet` is simultaneously the
`overflow-y: auto` scrollport, the element `syncSheetToViewport()` mutates
inline, and the element Chrome runs native scroll-into-view on. Split
those roles: move the header out of the scrollport so `.filter-sheet`
stops scrolling and a new inner `.sheet-body` wrapper scrolls instead.

Scope decision: apply to **all six sheets**, not just Add. This requires a
markup change, because Export, Insights, Settings/Manage and Transactions
each render the header plus several loose sibling `.field` blocks directly
under `.filter-sheet` with no single scrollable body element; only Add
(`#addForm`) and Import (`#importSheetBody`) already have one.

## Acceptance criteria

- [x] Attempt 1's `#addSheetBackdrop .filter-sheet { contain: paint; }`
      rule is removed — it is a confirmed on-device no-op, and leaving it
      in place would imply it does something.
- [x] All six sheets scroll from an inner `.sheet-body`, with the header
      pinned outside the scrollport; every sheet's own scrolling, header
      pinning, and close/save controls still behave on a real device.
- [x] Root cause identified via real-device inspection (remote debugging
      or equivalent) — not just re-confirmed to occur, but understood well
      enough to explain why the fix works. **Met via the "or equivalent"
      path, not `chrome://inspect`** — be precise about this if it matters
      later. The mechanism was isolated by two shipped on-device
      experiments rather than by inspecting a paint frame: attempt 1
      (`contain: paint`) changed nothing, which rules out a clipping
      failure since containment makes it spec-impossible for a descendant
      to paint outside the box; attempt 2 (splitting the scrollport from
      the resized box) eliminated it. That pair explains why the fix works
      — the artifact was a stale composited frame of a box being resized
      and scrolled at the same moment — but nobody ever watched the
      compositor do it.
- [x] Reproduced and confirmed fixed on a real device: open the Add sheet,
      focus the Note field, keyboard opens — no content ever paints above
      the sheet's rounded top edge at any point during the transition.
      Repeat several times (timing-sensitive bugs can be intermittent).
- [x] The existing keyboard-avoidance behavior `syncSheetToViewport()` was
      built for (sheet no longer gets dragged off-screen by the browser's
      native scroll-into-view on a short viewport — see
      `docs/CHANGELOG.md`'s "On-screen keyboard pushing the whole sheet
      off-screen" entry) still works, confirmed on the same real device.
- [x] `wireSheetDrag()`'s swipe-to-dismiss gesture and scroll-lock/focus-trap
      behavior (`createFocusTrap()`, shared by all six sheets) are
      unaffected on every sheet, not just Add.
- [x] Fix does not depend on desktop-only verification — the spec's
      Investigation section already confirmed desktop resize simulation
      does not reproduce this bug.

## Review notes

Record confirmed defects and their resolution here. Keep optional suggestions
clearly separate.

### Round 1 — attempt 1 (`contain: paint`), shipped as `81cb197`

Confirmed defects found in review, both since fixed by Codex:

1. The CSS comment stated the paint mechanism as established fact, when the
   spec had explicitly left it unconfirmed and no device inspection had
   happened. Rewritten to frame it as an unverified hypothesis.
2. The new e2e spec's geometry assertion
   (`type.bottom <= header.top || type.top >= header.bottom`) was satisfied
   by the buggy state itself — content painting *above* the header meets the
   first disjunct — so it could not fail for this bug. Compounding it,
   `getBoundingClientRect()` reports layout geometry and never paint
   clipping, so no DOM assertion in that file can observe the symptom. The
   assertion was removed rather than patched; the spec now states plainly
   that it guards the declaration and surrounding shared-sheet behavior
   only.

Outcome: **attempt 1 was disproven on the real device** — the maintainer
reproduced the ghosting unchanged after deploy. See the spec's Investigation
section for why that is a strong negative result (it points at a stale
compositor texture rather than a clipping failure) and do not retry
`contain: paint`.

### Round 2 — attempt 2 (`.sheet-body` scrollport), shipped as `cc5005f`

**The ghosting is fixed.** The maintainer confirmed on the real device that
attempt 2 eliminated it, which validates the approach: the bug came from
`.filter-sheet` being at once the scrollport, the inline-resized box, and
the scroll-into-view target, and separating those roles resolved it.

One regression followed from it, reported with a real-device photo and
fixed:

3. `.sheet-body` became the clip box but had no padding of its own, while
   the previous scroller (`.filter-sheet`) had `padding: 20px`. Anything
   painting outside a child's border box was therefore sliced. Two visible
   symptoms, one cause: `.input-wrap:focus-within`'s
   `outline: 2px solid` + `outline-offset: 1px` had its left/right segments
   cut off, and the category/account chip rows were cut mid-pill at the
   body's top edge — 16px below the header's divider (`.filter-sheet`'s
   `gap: 16px`) with bare card background above it, where the old sticky
   header used to hide that cut behind its opaque background. Fixed with
   matched negative margins and padding on `.sheet-body`, extending its
   clip box to the shell's edges without moving any content.

Verified in a real browser at phone width, not just by reading the CSS: with
the fix, a focused `.input-wrap`'s outline box sits 20px inside the
scrollport's clip box and the body's clip edge is flush with the header's
bottom border; temporarily zeroing the new margin/padding reproduces the
clipping, confirming the check is falsifiable.

Optional suggestions from round 1, deliberately not implemented: promoting
the rule beyond the Add sheet (moot — the rule is being removed), deferring
`syncSheetToViewport()`'s inline `max-height` write to a
`requestAnimationFrame` (still open as a fallback lever if attempt 2 fails),
and clearing the stale inline `transform` `wireSheetDrag()` leaves behind on
its dismiss path (`utils.js:270-272`, pre-existing and harmless).
